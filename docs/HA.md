# High availability

UCM can run on two or more nodes that share one PostgreSQL database. This page covers what a node needs, three ways to deploy it, what stays local to a node and what is refused in HA mode. The scheduler, leader election and rolling restart are described in [HA mode](ADMIN_GUIDE.md#ha-mode-scheduler-and-startup).

## Prerequisites

- **PostgreSQL 13 or later**, reachable by every node (`DATABASE_URL`). SQLite is refused at startup.
- **The same `SECRET_KEY` on every node** (`UCM_SECRET_KEY` in the Docker image). It signs the CSRF tokens until the session key is rotated from the web interface, which stores the new key in the database for every node; it then stays the fallback (see [ADMIN_GUIDE.md](ADMIN_GUIDE.md#session-key-rotation)).
- **The same `KEY_ENCRYPTION_KEY` on every node**, a Fernet key. It decrypts every private key in the database: losing it makes them unrecoverable. Do not keep a different `master.key` file on a node: a local file overrides the variable.
- **The same `UCM_DB_ENCRYPTION_KEY` on every node**, another Fernet key. It encrypts the integration secrets (DNS provider credentials, LDAP and AD bind passwords, SMTP and OAuth secrets, SSO client secrets, webhook secrets and tokens, ACME EAB and TSIG keys, Microsoft CA and HSM credentials, the scheduled backup password). Without it a node derives a key from its own machine identifier, so a secret saved on one node would not decrypt on another: a node with `UCM_HA=1` and no `UCM_DB_ENCRYPTION_KEY` refuses to start and names it. Back it up with the KEK.
- **A distinct `UCM_NODE_ID` per node** (default: the host name). Two VMs cloned from one image keep the same host name: set it explicitly. A node whose identifier a live node already uses refuses to start, see [Node identifier](ADMIN_GUIDE.md#ha-mode-scheduler-and-startup).
- **`UCM_HA=1`** on every node.
- **A load balancer** in front of the nodes. Probe `/health/ready`. UI sessions are stored in PostgreSQL (in Redis when `REDIS_URL` is set, see [REDIS.md](REDIS.md)) and shared by every node, so no request needs a given node, except the multi-request Kerberos handshake, and the balancer must pass the WebSocket upgrade, see [Session affinity](#session-affinity).
- **One gunicorn worker per node**, which is the default (`workers = 1`). Do not raise it.
- **Synchronised clocks** (NTP). Heartbeats, the node registry, cluster commands, the maintenance, the leases of the expiry alerts and scheduled CRLs, ACME order leases, the scheduled backup reservation, webhook and deployment delivery claims, discovery schedules and the cooldowns of notification e-mails are written and compared on the PostgreSQL server's clock, so a skew between nodes neither runs that work twice nor holds it back. Everything else is dated by the node that writes it and compared with the clock of the node that reads it: the expiry of sessions, API keys, reset links, ACME nonces and authorizations, SCEP challenges, approvals and lock-outs, purges by age, and the validity of certificates and CRLs move by the skew between two nodes.

Generate the keys once:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"                                       # SECRET_KEY
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"          # KEY_ENCRYPTION_KEY
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"          # UCM_DB_ENCRYPTION_KEY
```

## Deployment 1: Helm

Set `ha.enabled=true`, `replicaCount` to 2 or more and a PostgreSQL URL:

```yaml
ha:
  enabled: true
replicaCount: 2
database:
  type: postgresql
  existingSecret: ucm-database      # or databaseUrl: postgresql://ucm:...@db.example.com:5432/ucm
fqdn: ucm.example.com
ingress:
  enabled: true
  host: ucm.example.com
  annotations:
    nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"
```

The render fails with an explicit message when the database is not PostgreSQL or `replicaCount` is below 2, and, without `ha.enabled`, when `replicaCount` is above 1. In HA mode the chart:

- sets `UCM_HA=1` and `UCM_NODE_ID` to the pod name;
- keeps the startup probe on `/health/live` that every render has (`startupProbe`, 10 s × 36 by default): a container killed and restarted in its pod keeps the pod name and waits up to 190 s for its previous heartbeat to expire, and the liveness probe, which would restart it after about 100 s (three failures from 40 s, 30 s apart), starts only once it serves;
- puts `UCM_SECRET_KEY`, `KEY_ENCRYPTION_KEY` and `UCM_DB_ENCRYPTION_KEY` in one Secret, generated once and kept across upgrades, including when `ha.enabled` is later set to false (override with `secrets.secretKey`, `secrets.keyEncryptionKey` and `secrets.dbEncryptionKey`). The Secret carries `helm.sh/resource-policy: keep`, so `helm uninstall` leaves it; back it up. With `helm template` or GitOps (ArgoCD) there is no lookup, so the render refuses `ha.enabled=true` until `secrets.keyEncryptionKey` and `secrets.dbEncryptionKey` are set: keys drawn at each render would be written into the Secret without restarting the pods, which would start on them at their next restart while the data stays under the previous keys. `UCM_SECRET_KEY` and the initial admin password are drawn again at each such render too: set `secrets.secretKey` and `initialAdminPassword`;
- restarts the pods when a value the Secret is made from changes (`checksum/secret` is computed on the values you set, not on the generated ones, which never change once stored on a cluster);
- creates no `etc` volume or claim: the key comes from the Secret;
- updates with `RollingUpdate` (`maxUnavailable: 0`), adds a PodDisruptionBudget (`ha.podDisruptionBudget.minAvailable`, default 1) and a preferred pod anti-affinity that spreads the pods over hosts (your own `affinity` value replaces it);
- passes `redis.url` as `REDIS_URL` when set;
- uses an `emptyDir` data volume per pod, with a warning in the release notes, unless `persistence.data.existingClaim` names a ReadWriteMany claim.

### From a single node

Moving an existing single-node release to `ha.enabled=true` needs these steps, because HA requires PostgreSQL, the data volume is no longer mounted and the keys come from the Secret. On an existing release (`helm upgrade`), the render refuses `ha.enabled=true` until `secrets.keyEncryptionKey` and `secrets.dbEncryptionKey` are given or already in the Secret: it recognizes a single instance by a Secret without them, and generating them would make its private keys and integration secrets unreadable. A render that cannot reach the cluster (`helm template --is-upgrade`, `helm upgrade --dry-run` on the client side, `helm diff`) cannot read the Secret either: it refuses `ha.enabled=true` unless both keys are given in the values, and names `--dry-run=server`, which reads the Secret like a real upgrade. The chart tells the two apart by the namespace's `default` ServiceAccount, which only a render with cluster access finds in an existing namespace. `helm install --create-namespace` renders before it creates the namespace, so a first HA install into a new namespace finds neither and is refused the same way: create the namespace first (`kubectl create namespace <name>`) and install once its `default` ServiceAccount exists, which Kubernetes adds a moment later (`kubectl get sa default -n <name>` finds it), or set both keys in the values. The account that runs `helm` needs, on every render, `get` on `secrets` in the release namespace (the chart reads its Secret back whatever `ha.enabled` is) and, with `ha.enabled`, also `get` on `serviceaccounts` and `persistentvolumeclaims` in the release namespace: without them, the render stops with Kubernetes' `forbidden` error rather than a message from the chart. A node started with another KEK than the database's runs in safe mode (no write, `encryption_key_mismatch`) rather than encrypt under it.

0. If the release uses SQLite (the chart default), move it to PostgreSQL while still single-node: in Settings > Database, test the PostgreSQL URL and run **Migrate data and switch**, then `helm upgrade` with `database.type=postgresql` and that URL, and check the data in the UI. Setting `database.type=postgresql` alone starts on an empty database, and data migration is refused once in HA.
1. Copy the content of `/etc/ucm/master.key` (the `etc` volume) into `secrets.keyEncryptionKey`. A new key cannot decrypt the existing database.
2. Still single-node, give the release its database key and re-encrypt the integration secrets under it: `helm upgrade` with `secrets.dbEncryptionKey` set to a new Fernet key, then, in the restarted pod, `kubectl exec deploy/<fullname> -- sh -c 'cd /opt/ucm/backend && python -m scripts.rewrap_db_key'`. The pod's former key is derived from `/opt/ucm/data/.machine-key`, on the data volume HA pods no longer mount: this step must come before the switch. See [Re-encrypting the integration secrets](#re-encrypting-the-integration-secrets).
3. Back up the data volume. HA pods no longer mount it, so SoftHSM tokens, an uploaded HTTPS certificate and local backups stay behind in it. `helm upgrade` still renders the existing claim, unmounted and with `helm.sh/resource-policy: keep`, when its cluster lookup finds it; `helm template` and GitOps tools have no lookup and drop the claim from the manifest, so protect it on their side before the switch.
4. Stop the single instance, so that it never runs beside HA pods on the same database (outside the leader election, its scheduler would run the tasks a second time): `kubectl -n <namespace> scale deployment/<fullname> --replicas=0`, then `kubectl -n <namespace> wait --for=delete pod -l app.kubernetes.io/instance=<release> --timeout=300s`. The rolling update of the next step would otherwise keep the old pod running until the new ones are ready.
5. Run `helm upgrade` with `ha.enabled=true` and `replicaCount` 2 or more, then check `/health/ready`.

## Deployment 2: Docker Compose

`docker-compose.ha.yml` at the root of the repository starts PostgreSQL, two nodes and an HAProxy balancer with cookie affinity and a `/health/ready` probe. Create a `.env` file next to it with `POSTGRES_PASSWORD`, `UCM_SECRET_KEY`, `KEY_ENCRYPTION_KEY`, `UCM_DB_ENCRYPTION_KEY`, `HA_LB_CERT` (a PEM file with the certificate and key for the balancer) and `UCM_FQDN`, then:

```bash
docker compose -f docker-compose.ha.yml up -d --wait
```

HAProxy does not run as root: the PEM file must be readable by uid 99 (`chmod 644`, or `chown 99` with `chmod 600`). A file it cannot read makes haproxy exit at start, so the balancer restarts in a loop and its health check never gets to run; because the service declares one, Docker reports the stopped container unhealthy and `docker compose up --wait` exits with an error within seconds (`container ... is unhealthy`). Without a health check, `--wait` returned success on that looping balancer. Without `--wait`, `docker compose ps` shows it `Restarting` and its log says `cannot open the file '/certs/lb.pem'`.

Without a password for the first administrator, the node that creates it generates one in its own data volume: `docker compose -f docker-compose.ha.yml logs ucm-1 ucm-2 | grep 'Initial administrator'` names that node (the other one logs `file is on node ucm-N`), then `docker compose -f docker-compose.ha.yml exec ucm-N cat /opt/ucm/data/initial-admin-password` reads it.

Compose refuses to start while one of these variables is missing. The balancer listens on port 8443. The image entrypoint writes no SQLite path and takes no SQLite backup copy when `UCM_HA=1`. Keep the restart policy `unless-stopped` or `always`: a rolling restart exits each container in turn.

The network uses the fixed subnet `172.28.0.0/24`, trusted as the proxy. When `up` fails with "Pool overlaps", another Docker network already holds that range: set `UCM_HA_SUBNET` in `.env` to a free one.

## Deployment 3: DEB or RPM on two hosts

1. Install the package on both hosts.
2. In `/etc/ucm/ucm.env` on each host set the same `DATABASE_URL`, `SECRET_KEY`, `KEY_ENCRYPTION_KEY` and `UCM_DB_ENCRYPTION_KEY`, `UCM_HA=1`, and a different `UCM_NODE_ID` (a host cloned from the other keeps its host name, the default). The packages generate a random key per node at install: replace it on both hosts.
3. Every node must hold the same encryption key: either no `/etc/ucm/master.key` and `KEY_ENCRYPTION_KEY` in `ucm.env`, or the same `master.key` copied to every node (a local file wins over the variable).
4. Restart `ucm` on each host, one at a time, and check `/health/ready` through the balancer (HAProxy, nginx or any layer 7 balancer; it must pass the WebSocket upgrade, see [Session affinity](#session-affinity)).

## From one node to a cluster

A cluster needs one PostgreSQL that every node reaches, and the same secrets on every node. Whatever the packaging, the steps are the same; the Helm variant is in [From a single node](#from-a-single-node).

**Identical on every node:** `DATABASE_URL`, `SECRET_KEY` (`UCM_SECRET_KEY` in Docker), the key-encryption key (`KEY_ENCRYPTION_KEY`, or the same `master.key` file), `UCM_DB_ENCRYPTION_KEY`, `UCM_HA=1`. **Different on each node:** `UCM_NODE_ID`. A node whose key-encryption key differs from a live peer's refuses to start (see [Shared encryption key](#shared-encryption-key)).

1. **Move the existing node to PostgreSQL, still alone.** On SQLite, open Settings > Database, test the PostgreSQL URL and run **Migrate data and switch**. The migration is refused once `UCM_HA` is set, so it comes first. Under Docker it migrates without switching: set `DATABASE_URL` in the container environment and restart the container before you check the data. Check the data in the web interface.
2. **Keep the secrets.** The existing node's `master.key` (or its `KEY_ENCRYPTION_KEY`) and `SECRET_KEY` become the cluster's: a new key cannot decrypt the database.
3. **Give the node its database key, still alone.** Without `UCM_DB_ENCRYPTION_KEY` its integration secrets are under a key derived from its machine identifier, which no other node has. Set a new `UCM_DB_ENCRYPTION_KEY` (or keep the one it already has), restart it, and re-encrypt them, see [Re-encrypting the integration secrets](#re-encrypting-the-integration-secrets).
4. **Set `UCM_HA=1` on that node** (in `/etc/ucm/ucm.env` for DEB and RPM, in the container environment for Docker), give it a `UCM_NODE_ID`, and restart it. Shortly after it starts, it must answer `200` on `/health/ready`.
5. **Add each further node** with the same `DATABASE_URL`, `SECRET_KEY`, `UCM_DB_ENCRYPTION_KEY` and key-encryption key (copy `master.key` to the same path, or set `KEY_ENCRYPTION_KEY` and leave no `master.key`), `UCM_HA=1` and its own `UCM_NODE_ID`. Start them one at a time. The packages generate a random key per node at install: replace it. With Compose, `docker-compose.ha.yml` sets all of this for two nodes; to reuse the PostgreSQL of step 1, set `DATABASE_URL` in its shared `x-ucm-node` block and drop the `postgres` service with the `depends_on` that waits for it.
6. **Put the nodes behind the load balancer.** Probe `/health/ready` over HTTPS (the nodes serve their own certificate, on port 8443 by default). Set `UCM_BEHIND_PROXY=1` and `UCM_TRUSTED_PROXIES` to the balancer's address on every node, or every client appears to come from the balancer. See [Behind the load balancer](#behind-the-load-balancer) for affinity, rate limits and ACME challenges.

What does not follow the database: SoftHSM tokens, files a node mirrored on its disk, and archives written before HA (see [What stays local to a node](#what-stays-local-to-a-node) and [Backups](#backups)). A node does not create the first administrator again: it exists in the database.

### Checking the cluster

- `/health/ready` through the balancer answers `200` for each node in turn. A node answers `503` while it has never registered in `cluster_nodes`, while another live process uses its identifier, and during a restore (see [Restoring a backup](#restoring-a-backup)).
- `/health` reports `ha`, `node_id`, `leader` and, in HA mode, `cluster: {leader_node_id, nodes, stale}`: every node running is counted in `nodes`, none should be in `stale`, and `leader_node_id` names exactly one. A node stopped cleanly gave its row up and is counted in neither, at once; a node killed or cut off is counted in `stale` after three passes (3 minutes) without a heartbeat. After 15 passes (15 minutes, as long as an update campaign waits for a node) a row is counted nowhere, and the leader deletes it at its next pass once it has led for three passes. This matters under Kubernetes, where `UCM_NODE_ID` is the pod name and a replaced pod never comes back; a node that comes back under a deleted identifier writes a new row with its first heartbeat.
- `GET /api/v2/system/service/status` lists rows up to the same 15 minutes, nodes stopped cleanly included.
- `GET /api/v2/system/service/status` (signed in) lists every node with its version, heartbeat, `command_seen`, `kek_fingerprint` and `package_family`: the fingerprints must be equal.
- The status bar of the web interface shows the node that answers, whether it leads, the number of nodes and how many are late.

## First administrator

The administrator is created once, by the first node to start, under the startup lock. Provide its password through a secret shared by the nodes (`INITIAL_ADMIN_PASSWORD_FILE`; the Helm chart passes `UCM_INITIAL_ADMIN_PASSWORD` from its Secret to every pod), or let that node generate it: only that node then writes `initial-admin-password`, and every node's log says which node holds it. The password change at first login removes the file wherever it is. See [ADMIN_GUIDE.md](ADMIN_GUIDE.md#initial-administrator-password).

## Backups

Scheduled and manual archives are stored in PostgreSQL (`backup_archives`, and the archive itself in chunks of 1 MiB in `backup_archive_chunks`), encrypted as on disk, with the node that wrote it, its date, size and SHA-256. Every node lists the same archives (Settings > Backup shows the node) and downloads any of them, also when the node that wrote it is gone; the download carries the SHA-256 in a `Repr-Digest` header. An archive appears once it is whole: an export that fails or a node that dies mid-write leaves nothing behind. Retention runs once, on the leader (and on demand from any node, one at a time across the cluster), over the whole set, with the rules of a single node (age, the newest archives always kept); each archive is read back before it is stored, so none counts as unproven. Archives a node kept on its disk before HA are no longer listed; copy them off the host. Writing an archive holds one transaction for as long as it lasts, so its connection lifts `idle_in_transaction_session_timeout` for that transaction: a server that sets it, as managed PostgreSQL services often do, does not cut a slow backup short. A download reads each chunk in a short transaction of its own and holds no connection between two, so slow clients do not exhaust a node's connection pool; an archive deleted during a download ends it short of its `Content-Length`, never with other bytes.

An archive kept in the database does not survive the loss of that database: download the archives you keep to a place outside the cluster, and back PostgreSQL up with its own tools (to restore such a dump, see [Restoring with PostgreSQL's tools](#restoring-with-postgresqls-tools)). Each archive adds about its own size to the database and to its dumps, so the database holds what retention keeps: with the default 30 days and daily backups, about 30 archives, and never fewer than the 2 newest. A ceiling on the total size (Settings > Backup, `max_total_mb`) bounds that: retention removes the oldest archives, auditing each, until the total fits, except the `backup_min_keep` newest (2 by default), so the total can stay above the ceiling, which is reported. `pg_dump --exclude-table-data=backup_archives --exclude-table-data=backup_archive_chunks` leaves them out of a dump.

## Restoring a backup

An archive is restored from any node, from Settings > Backup or `POST /api/v2/system/restore`. The node that receives it holds a cluster maintenance (one row in `cluster_maintenance`) for the whole restore. Before setting it, that node checks the password, the archive's header and its first chunk (an archive in an older format is read whole): a wrong password, a file that is not a backup, an archive written by a later release, or an Argon2id archive in FIPS mode answers `400` without touching the other nodes. An archive damaged further on, or one whose checksum does not match, is refused under the maintenance, which is then lifted with nothing changed.

1. Every process of every node reads the maintenance within about 2 seconds and from then on refuses writes, then records it in `cluster_nodes` (`maintenance_ack` for the web worker, `maintenance_ack_scheduler` for the process that runs the scheduled tasks).
2. The restore starts once both processes of every node with a fresh heartbeat have recorded it. After 30 seconds without, it is refused with `409` and code `maintenance_not_acknowledged`, the silent nodes listed in `nodes` with the process missing; nothing is changed and the maintenance is lifted. A node that died counts until its heartbeat is stale (3 minutes).
3. The restore is one transaction, as on a single node. Just before its commit it checks, in that transaction, that the maintenance is still its own and within its lease; otherwise everything is rolled back (`409`, code `maintenance_lost`).
4. Once it commits, the sessions are revoked and the CRLs signed again, as on a single node, then a rolling restart is requested. A process started after that request serves again; every node not restarted yet keeps refusing writes and answering 503 on `/health/ready`. The maintenance is lifted once every node with a fresh heartbeat has restarted.

After the commit, every node makes its certificate and key files match the database at its turn of the rolling restart (the cluster stays in maintenance until then, and no node's files move before it), whether its directories are its own (the chart's `emptyDir`) or shared by every node: it writes the files that are missing or differ and removes those of the rows the restore removed (see [Files after a restore](ADMIN_GUIDE.md#files-after-a-restore)). Nodes sharing a directory take turns, through a PostgreSQL advisory lock keyed by an identifier written once in the directory (`.ucm-files-id`); nodes with directories of their own run at the same time. The HTTPS certificate and key of the archive stay in the database and every node serves them from its turn of the rolling restart, as it does a regenerated one, until a certificate is bound or regenerated, or a later restore replaces them.

A restore that fails leaves the database as it was, lifts the maintenance and answers the error. An archive that carries no data lifts it with no restart. Sessions, archives encrypted by another installation and archives of older versions follow the single-node rules (see [ADMIN_GUIDE.md](ADMIN_GUIDE.md#restoring-backups)).

### What a node in maintenance serves

- Writes are refused with `503`, `Retry-After: 30` and code `maintenance`: every `POST`, `PUT`, `PATCH` and `DELETE` of the API (sign-in included) and every request to ACME, EST, SCEP, MS-XCEP, MS-WSTEP and TSA, whatever its method. A write the node's own code still sends (a read that writes, a task already running) fails the same way, and so does the commit of a transaction that wrote before the node saw the maintenance.
- No scheduled task starts, on the leader as on the others; a "run now" waits for the end. The heartbeat goes on, and no session is saved.
- No background job starts: `GET` and `POST /api/v2/audit/verify` and the manual backup routes (`POST /api/v2/system/backup`, `/api/v2/system/backup/create`, `/api/v2/settings/backup/create`) answer `503` with `Retry-After: 30` and the message `A cluster maintenance is in progress, no background job starts until it ends`, as a restore may replace what the job would read. A job already running is followed at `GET /api/v2/system/jobs/<id>` and concludes once the maintenance ends.
- `/health/ready` answers `503` with `status: "maintenance"`, so the balancer takes the node out of rotation; `/health` and `/health/live` answer 200, and `/health` reports `maintenance` (reason, phase, node, lease).
- Reads of the API and the web interface are served, as are `GET` and `DELETE /api/v2/system/maintenance`.
- OCSP, CRL distribution points and AIA keep answering from the state before the restore: relying parties keep validating certificates, a client that fails hard on a missing revocation answer is not cut off, and the answer is at most one restore old. Meanwhile no OCSP response is stored and no CRL is signed: a CRL past its next update is served as it is, and a CA with no stored CRL answers `503` with `Retry-After`.
- Socket.IO connections are answered before the request hooks and are not covered.

A node that starts while a restore has not committed yet waits for its end before migrating or writing, and says so in its log.

### When the restoring node dies

The maintenance has a lease of 5 minutes, renewed every 30 seconds while the restore runs. A restore that had not committed is rolled back by PostgreSQL with the node's connection, and the first node that sees the lease ended lifts the maintenance. A restore that had committed is completed by the first node that sees its lease ended: it revokes the sessions and requests the rolling restart, as the restoring node would have. The rolling restart phase has a lease of 30 minutes. An administrator lifts the maintenance at once from any node with `DELETE /api/v2/system/maintenance`, which first completes a committed restore the same way.

### Restoring with PostgreSQL's tools

`POST /api/v2/system/maintenance` with `{"lease_minutes": 60}` (1 to 1440) sets the same maintenance by hand. It answers once every node with a fresh heartbeat has recorded it, or `409` naming the others and lifts it; posting again extends it, `GET` shows it with each node's acknowledgement, `DELETE` lifts it. A manual maintenance survives a restart of the nodes.

Before restoring a `pg_dump`, make sure every node runs with the key-encryption key of the installation that was dumped (`KEY_ENCRYPTION_KEY` or `master.key`): the data-encryption keys in `encryption_keys` are wrapped by it. The tables that describe the running cluster are not data to restore: `cluster_nodes`, `cluster_commands`, `cluster_maintenance`, `scheduler_requests`, `websocket_relay` and the sessions (`user_sessions`, `pro_sso_sessions`, and `flask_sessions` on PostgreSQL without Redis).

- **Nodes stopped** (simplest): stop every node, run `pg_restore --clean --if-exists`, empty the tables above (`TRUNCATE`), and with Redis sessions delete the keys under `SESSION_KEY_PREFIX` (default `ucm:session:`). Start the nodes one at a time: a dump of an earlier release is migrated by the first one.
- **Nodes running**: set the maintenance, list the dump (`pg_restore -l dump > list`), remove the lines of the tables above from `list`, run `pg_restore --clean --if-exists -L list`, empty the session tables, restart every node with its service manager (`systemctl restart ucm`, `kubectl rollout restart`, `docker compose restart`), then lift the maintenance. The nodes refuse writes until it is lifted, and `--clean` drops the tables they read while it runs, so expect errors on reads meanwhile.

## Behind the load balancer

### Session affinity

Sign-in sessions do not need it: they are stored in PostgreSQL (in Redis when `REDIS_URL` is set), so any node accepts a session another one opened. Only the Kerberos handshake depends on the node that received the first request:

- **Socket.IO needs no affinity, but the balancer must pass the WebSocket upgrade.** The UI opens a WebSocket only and never falls back to HTTP requests. One WebSocket is one connection to one node, and the sign-in session is shared, so any node can accept it. A balancer that does not pass the upgrade gives no live updates whatever its affinity: the browser retries 5 times, then stops until the page is reloaded. Events emitted on one node reach the browsers connected to the others (through PostgreSQL, or Redis when set).
- **Kerberos enrollment.** A SPNEGO handshake of more than one request needs source-address affinity, see [Windows enrollment](#windows-enrollment-kerberos).

### Rate limits

Rate limits are counted per node, in memory, and are not shared. Two layers apply. The first is flask-limiter, fixed in code and not set in Settings: 200 requests per minute and 2000 per hour per client address on every route without its own limit, and per-route limits such as 5 per minute on password, LDAP and WebAuthn sign-in and 10 per minute on the two-factor routes. The second is the UCM limiter of the API and the protocol endpoints, in tiers set by environment variables (`RATE_LIMIT_AUTH_RPM`, `RATE_LIMIT_HEAVY_RPM`, `RATE_LIMIT_STANDARD_RPM`, `RATE_LIMIT_PROTOCOL_RPM` and their `_BURST` counterparts). Settings > Security changes only the limits per path, the global switch and the whitelist, and those changes reach every node. Clients on private networks are exempt on every node by default (`RATE_LIMIT_TRUST_LAN`). The counters do not reach the other nodes. A client address that the balancer spreads over N nodes can therefore make up to N times the lower limit, burst included: 200 × N requests per minute on the standard API routes, 60 × N on the heavy tier (certificate issuance and the `/api/v2/cas` prefix, CA import and export included), 20 × N on `/api/v2/import` (file and OPNsense import), and 5 × N password sign-ins per minute; other prefixes have their own tier. A client that keeps one connection to one node meets the configured limit; protocol clients (ACME, EST, SCEP, OCSP) and scripts are usually spread. The lock-out of an account after failed sign-ins is stored with the user in the database and counts across nodes. The limits use the client address, so set `UCM_BEHIND_PROXY=1` and `UCM_TRUSTED_PROXIES` to the balancer's address, or every client shares the balancer's.

### ACME challenges

- **HTTP-01** (client orders): the answer is read from the database, so any node can serve the challenge file when the CA's request reaches it.
- **TLS-ALPN-01**: the node that runs the validation opens a listener on the port set in the ACME client settings (443 by default), on all its addresses, for the duration of the challenge. That is the node that received the request for a manual validation, and the scheduler leader for an automatic renewal. The CA connects to port 443 of the identifier's name, which must reach that node's listener (directly, or forwarded to the configured port): a layer 7 balancer that terminates TLS cannot pass the proof, and a TCP balancer that spreads connections over the nodes reaches the listener only when it happens to pick that node. Route the port to a single node, or use HTTP-01 or DNS-01 behind a balancer.
- **DNS UPDATE (RFC 2136) listener of the ACME proxy**: every node with a port configured runs its own listener, UDP and TCP; the port is read when the node starts, so a change in Settings reaches each node at its own restart, and `UCM_DNS_UPDATE_PORT` is that node's alone. The TXT values a client sends are stored in PostgreSQL, so the node that answers the CA's DNS query does not matter. What each node keeps in memory: the expected challenges, reloaded at most every 5 seconds as on a single node (a proxy account deleted or disabled on one node still has its pending values accepted by the others for up to 5 seconds); the zones it answers for, taken from the ACME domains, reloaded at most every 10 seconds and at once only on the node that changes a domain (a domain just added is unknown to the other nodes, and one just removed still accepted by them, for up to 10 seconds); the TSIG keys, reloaded at most every 30 seconds (a key just created is unknown to the other nodes, and one just revoked or whose account was disabled is still accepted by them, for up to 30 seconds); the replay cache of signed requests (a request replayed to another node within its TSIG time window is processed again rather than answered from the cache; storing the same TXT value twice changes nothing); its packet rate limits (N nodes accept up to N times the configured rate); and the listening status Settings shows, which is that of the node that answers. Point clients at one address that reaches any node's listener, UDP and TCP.

## What stays local to a node

- **Update result.** The outcome of an update is read on the node that installed it, leader or not.
- **Per-node task status.** The scheduler view shows the update result runs of the node that answers, and Run now runs them on that node.
- **SoftHSM tokens.** A token lives on the node's own disk, so UCM refuses to create one in HA mode (see [Refused in HA mode](#refused-in-ha-mode)). A SoftHSM provider already in the database stays visible, a warning at start names it, and its keys sign only on the node that holds the token. Software CA keys stored in PostgreSQL under the shared `KEY_ENCRYPTION_KEY` work on every node; keys kept in an HSM must use a network HSM (PKCS#11 over the network, OpenBao, Azure Key Vault, AWS CloudHSM, Google KMS).
- **Kerberos negotiation state.** A SPNEGO handshake that takes more than one request is kept in the memory of the node that received its first leg (see [Windows enrollment](#windows-enrollment-kerberos)).
- **Certificate files** mirrored by renewals and session file cleanup, which run on the leader only.
- **The self-signed HTTPS certificate** of each node, as long as none was applied or regenerated from the web interface. Once one is, every node writes it from the database before it starts (see [ADMIN_GUIDE.md](ADMIN_GUIDE.md), HA mode).

## Scheduled passes across nodes

The `certificate.expired` webhooks resume from the last pass on any node, at most 30 days back, as on a single node. A pass of the expiry alerts or of a CA's scheduled CRL skipped because another node holds its lease runs once more 30 seconds after that lease ends, instead of waiting a day or an hour. The CRL lease lasts 15 minutes and is not renewed while the CRL is signed: a signature that takes longer lets another node sign the next CRL too, so two CRLs of consecutive numbers are published, which changes nothing for clients: UCM serves the CRL of the highest number. Size a slow HSM provider so that a CRL signature stays well under 15 minutes. See [ADMIN_GUIDE.md](ADMIN_GUIDE.md#ha-mode-scheduler-and-startup).

## When PostgreSQL is unavailable

Every node depends on the database for requests, sessions, the leader lock and the heartbeat, so a cut of PostgreSQL stops the cluster, not a node. What each node does:

- **Probes.** `/health/ready` answers `503` as soon as `SELECT 1` fails, or after 5 seconds without an answer when the server neither answers nor refuses (a frozen server, an address that no longer routes); it then reads nothing else from the database, so the balancer takes every node out of rotation, and `200` again at the first probe after the database returns. `/health/live` reads nothing from the database, neither does any request hook for the two probes, so it answers `200` at once whatever the database does and an orchestrator does not restart nodes for it; `/health` keeps answering, with `cluster: null` when the registry cannot be read, after the connection timeouts below when the server does not answer.
- **Requests.** Any request that reads or writes the database fails, sign-in and sessions included, as long as the database is unreachable. On PostgreSQL the connection pool checks each connection before lending it and replaces one the cut broke, so the first requests after the database returns succeed. A new connection gives up after 10 seconds (`connect_timeout=10`), TCP keepalives (`keepalives_idle=30`, `keepalives_interval=10`, `keepalives_count=3`) close a connection whose server stopped answering after about a minute, and a query the server never acknowledges ends its connection after 30 seconds (`tcp_user_timeout=30000`); the same names in the `DATABASE_URL` query string take precedence. The pool keeps `pool_timeout` of 30 seconds and `pool_recycle` of 30 minutes (`DB_POOL_TIMEOUT`, `DB_POOL_RECYCLE`).
- **Network partition.** When packets are dropped instead of refused, opening a connection fails after 10 seconds, a pooled connection waiting on a silent server is closed by its keepalives after about a minute, and one whose query the server never acknowledges after 30 seconds (`tcp_user_timeout`), instead of the operating system's retransmission timeout of about 15 minutes. The scheduler lock connection uses the same keepalives and connect timeout, and also sets them on the server side with a 60-second `tcp_user_timeout`, so a leader cut off from the database notices and stops starting tasks, and PostgreSQL frees its lock.
- **Scheduler.** The leader checks its lock before each task. When the dedicated connection holding it is gone, it logs `Scheduler leadership lost`, starts no further task (one already running is not interrupted) and tries to take the lock again every 5 seconds. Every node does the same from the moment the database answers: the first to take it leads, which is not necessarily the previous leader.
- **Heartbeat.** A failed heartbeat is logged once, until the next one succeeds, and tried again at the next turn of the scheduler loop: after `LOCK_RETRY_SECONDS` (5 seconds) on a node that does not lead, after the 60-second pass (`WAKE_INTERVAL_SECONDS`) on the leader. After three passes (3 minutes) without one, other nodes count a node as stale: during a longer cut `/health` shows every node late until the heartbeats resume. The leader deletes no row of the registry before it has led for three passes, so a cut longer than 15 minutes removes no live node.
- **Settings commands and WebSocket events.** The applier of setting changes and the WebSocket relay reopen their connections by themselves and read what they missed.

### Re-encrypting the integration secrets

`python -m scripts.rewrap_db_key`, run from the `backend` directory (`/opt/ucm/backend`) with the service's environment, re-encrypts every integration secret under the `UCM_DB_ENCRYPTION_KEY` of that environment. It reads them with the key the host used while `UCM_DB_ENCRYPTION_KEY` was unset (derived from `/etc/machine-id`, or from `/opt/ucm/data/.machine-key` when the machine identifier is empty, as in a container), so run it on the host or in the container whose secrets they are. To move from one explicit key to another, put the previous one in a variable and name it: `--from-env OLD_DB_KEY`. `--dry-run` counts without writing.

- DEB/RPM: `cd /opt/ucm/backend && sudo -u ucm /opt/ucm/venv/bin/python -m scripts.rewrap_db_key`, after adding `UCM_DB_ENCRYPTION_KEY` to `/etc/ucm/ucm.env` and restarting `ucm` (the command reads `ucm.env` as the service does).
- Docker: `docker compose exec <service> sh -c 'cd /opt/ucm/backend && python -m scripts.rewrap_db_key'`, once the container runs with `UCM_DB_ENCRYPTION_KEY`.

It can run again: a secret already under the new key is skipped, and when every secret already is, it says there is nothing to do and exits 0, even on a host with no machine-derived key to read from. A secret that neither key opens stops it before anything is written, and the list names each one (table, row and column, never a value): enter those secrets again in the web interface, or clear them, then run it again. Nothing is printed or logged but names and counts. In HA, each node logs at start, as an error, the secrets that `UCM_DB_ENCRYPTION_KEY` does not open, and keeps serving; the integration that needs one fails and says so (a webhook is not sent unsigned, a mail is not sent without its SMTP login, an SSO login is not attempted without its client secret, an LDAP sign-in or the AD connector does not bind without its bind password, Intune validation does not start without its client secret, an HSM provider does not connect without its PIN, token or credentials).

## Shared encryption key

Every node holds the same key-encryption key (KEK): `KEY_ENCRYPTION_KEY`, or the same `master.key` on every node. The data-encryption keys it wraps live in the database (`encryption_keys`), so enabling, disabling, encrypting all keys and rotating the data key work from any node; the others reload the keys within seconds (`reload_encryption`). Each node publishes the fingerprint of its KEK (a truncated hash, never the key) in `cluster_nodes`, and a node whose fingerprint differs from a live peer's refuses to start and names that peer, unless the database names its KEK and not the peer's. Enabling encryption is refused (409, naming the node) while a live node holds another KEK. Back up the KEK: the database without it is unreadable. See [Private-Key Encryption](ADMIN_GUIDE.md#private-key-encryption-kek-and-dek).

## Windows enrollment (Kerberos)

The Windows enrollment profiles, their connectors and the switches are in the database, so every node serves them. Two things are per node:

- **SPNEGO state.** Some Windows clients need more than one request to complete the Negotiate handshake (a request-MIC leg). The context in progress is kept in the memory of the node that answered the first leg, under the client's source address (the address behind the trusted proxy when there is one), and expires after 30 seconds. The balancer must therefore send the requests of one client address to one node: use source-address affinity for the two Kerberos endpoints (`/ADPolicyProvider_CEP_Kerberos/` and `/ADCertificateService_CES_Kerberos/`); the web interface needs no affinity. Two clients behind one address that negotiate at the same moment can make each other retry, never authenticate wrongly.
- **The keytab file.** A profile's keytab is stored in the database, under the master key. UCM composes the keytabs of all profiles into one file, stores it in the database and asks every node to write it (`reload_keytab`, within seconds, and at each start); the composition is made under a lock, so two uploads at once give one result on every node. A node that cannot read the stored keytab (a different `KEY_ENCRYPTION_KEY`) cannot write the file and logs the reason. A keytab found on one node only, as 2.x kept it, is not shared in HA: upload it again.

## Refused in HA mode

These operations answer `409` with code `ha_mode`, because they only change the host that receives the request:

- backend switch and data migration between databases (`database.py`): change `DATABASE_URL` by hand, then restart;
- session key rotation without encryption (it would write `ucm.env`); with the KEK every HA node holds, it is stored in the database and works from any node, see [Session key rotation](ADMIN_GUIDE.md#session-key-rotation);
- creating a SoftHSM provider, pointing a provider at SoftHSM, generating a key on a SoftHSM provider, syncing the keys of a SoftHSM provider, and creating a CA (root, intermediate, external CSR or SSH) on a new or an existing SoftHSM key (the token is on one node's disk). Creating a CA on a key of a provider whose module is a local smart card reader module, OpenSC (`opensc-pkcs11.so`) or YubiKey PIV (`libykcs11.so`), is refused the same way: the reader is attached to one host. Any other PKCS#11 module is assumed reachable from every node. A CA already bound to a SoftHSM key keeps signing on the node that holds the token. The image does not initialize its default token when `UCM_HA` is set, whatever `HSM_AUTO_INIT` says. Network PKCS#11, OpenBao and cloud KMS providers are not affected.

## Upgrading

Upgrade the nodes one at a time, unless the release notes say that the release requires every node stopped. Migrations run under a PostgreSQL advisory lock: the first node to start applies them, the others wait and find nothing to do. A release only adds to what the release before it reads and writes, so the nodes not yet upgraded keep working during the roll. Keep the nodes on adjacent versions during the roll, and do not run an older version after a newer one migrated the schema.

A release that removes or narrows something the release before uses requires a full stop: its notes say so. Its `full-stop-migrations.json` asset names every migration that carries the full-stop mark, older ones included; those the database has not applied yet are the ones that require every node stopped. Stop every node, upgrade each one, then start them: a node stopped cleanly says so in `cluster_nodes` when it exits, so the first upgraded node applies the migration at once, even when its package starts it right after the install. A node that was killed or lost (power cut, `SIGKILL`) keeps its last heartbeat for three scheduler passes (three minutes): a node that starts with such a migration pending waits for it, up to three minutes and 15 seconds, without holding the startup lock, and logs every 15 seconds the nodes it waits for. If a node of another version still beats after that, the starting node refuses to apply the migration and does not start; its log names those nodes. With Helm or Compose, which roll the pods or containers themselves, stop every replica before the upgrade.

The move from 2.x to 3.0 is a full stop: stop every node, then start them on 3.0. A cluster moves to 3.0 from 2.254 only: bring every node to 2.254 first; a 3.0 node refuses to start, without writing, on a database 2.254 has not started (see UPGRADE.md).

- **Helm:** `helm upgrade` rolls the pods with no unavailable pod; the PodDisruptionBudget protects them from node drains. A stopping pod first leaves the Service's endpoints: its `preStop` hook sleeps `lifecycle.preStopSleepSeconds` (10 s) before UCM receives `SIGTERM`, so new connections go to the other pods; requests in progress then get 30 seconds to finish. `terminationGracePeriodSeconds` (60 s) covers the sleep and UCM's clean stop, at most 35 seconds, and the render refuses a value below `lifecycle.preStopSleepSeconds` + 35. A client that keeps a connection open to a stopping pod opens a new one when that pod closes it.
- **Compose:** `docker compose -f docker-compose.ha.yml pull`, then `up -d ucm-1`, wait until it is healthy, then until the balancer has it back: `docker compose -f docker-compose.ha.yml logs --since 5m lb | grep 'Server ucm/ucm-1 is UP'` (HAProxy logs each change of state; it checks every 2 seconds and takes a node back after two good answers). Only then `up -d ucm-2`, and wait the same way for `ucm-2`. Docker reports a node healthy before the balancer routes to it again: stopping the other one in between leaves no server for a few seconds (503 "No server is available"). A request sent to a node that is stopping is retried on the other one (`option redispatch`); a request already being served by it when it stops can still fail. Each node has 45 seconds to stop (`stop_grace_period`), the time of a clean stop, before Docker kills it.
- **DEB/RPM:** upgrade and restart one host, wait for `/health/ready`, then the next. Or install the update from the web interface (Settings > Updates), or let the scheduled automatic install do it: in HA mode either starts a rolling update.

### Rolling update from the web interface (DEB/RPM)

One campaign runs at a time. The scheduler leader gives the turn to one node at a time, in `UCM_NODE_ID` order, among the nodes with a fresh heartbeat when it starts. Each node installs the package of its own family, reported in `cluster_nodes.package_family` at every heartbeat: `deb`, `rpm-el9`, `rpm-el10` (any `rpm-elN`) or `rpm-fedora` (an RPM host of no EL release). At the start the campaign records one package per family present among the nodes beating, with its SHA-256 from the release; it refuses to start, naming the node and the reason, when a node runs Docker or Kubernetes (`container`) or an unknown packaging, or when the release has no package for a present family or no SHA-256 for it. An EL host whose release has no `.elN.` build is offered the Fedora RPM, which installs only where the system `python3` is 3.12 or later (it does not on EL8), and the campaign refuses only when the release has no RPM at all. On its turn, a node takes the entry of the family it detects itself, checks that the command carries the SHA-256 frozen at the start for that family, downloads and verifies the package, then asks its own update watcher to install it. The next node starts only once the previous one has a fresh heartbeat on the target version in `cluster_nodes`. A node already on the target is counted done without an install.

The campaign stops, and leaves the remaining nodes alone, when a node fails to download or verify the package, has a family the campaign holds no package for (a node that joined after the start; one that joins with a family present takes a turn), comes back on another version, or is not back on the target within 15 minutes (download, install, migrations under the startup lock and the first heartbeat). It refuses to start, before any node installs anything, when the release's `full-stop-migrations.json` names a migration the database has not applied, and when the release publishes no such file or it cannot be read; the message names the migration and its reason. Upgrade such a release with every node stopped. The scheduled automatic install starts nothing while the release still lacks the package of a family present, the `.sha256` file beside it, or its `full-stop-migrations.json`, and tries again at the next check: an upload in progress does not use up its one attempt at that version. Every step is audited and pushed to the browsers. Settings > Updates shows the target, the nodes done, the node in progress and the node where it stopped with the reason; fix that node, then **Resume** continues from it. Nodes without a fresh heartbeat at the start are listed as skipped and not updated; the end message names them.

While the campaign runs, the updated nodes and the others share the database. The first updated node applies the target's migrations, which only add to what the older version uses: the nodes not yet updated keep serving until their turn.

In Docker and Kubernetes the route and the scheduled install refuse with a message: the orchestrator updates the image (`docker compose pull`, `helm upgrade`).

During a roll from a version without the scheduled backup's conclusion marker, a scheduled backup run by an older leader is not marked as concluded: a newer leader then writes one extra archive two hours later, once.
