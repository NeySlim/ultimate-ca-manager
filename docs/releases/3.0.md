UCM 3.0 Phare is a major release. The console is rebuilt from the ground up, UCM now runs as a cluster of several nodes, and approvals, Windows enrollment and backups have been reworked. It upgrades any installation running UCM 2.254: read **Upgrading from 2.x** below before you install it.

## A new console

- **New layout.** A top bar replaces the sidebar. It holds the modules in four groups, three modules you can pin, global search, notifications, help and the account menu. A status bar shows the version, the cluster node, the live connection, and what is pending or running.
- **Two themes, Atelier and Aurore**, each in dark, light or following the system.
- **An Overview home page.** Four headline figures and nine cards: work queue with its actions, automation health, issuances by source, expiry horizon, compliance, revocation coverage, hierarchy, latest operations, authorities and HSM. You can show, hide and reorder the cards, and save layouts per user. Every figure opens the certificate list filtered to exactly what it counts.
- **An inspector on every list.** Objects open in a tabbed dock beside or under the list, several at a time, and stay open across pages. The address keeps them, so a reload or a shared link reopens the same view.
- **Detached windows and comparison.** Any certificate, authority or request can open in its own window over the page. Two to four certificates can be compared side by side, with the differences marked.
- **Search** that lists pages, actions and objects, a **comment** on each certificate, and a **session lock** on demand (Alt+Shift+L).
- **Built-in help and guide** in English, French, Spanish, Russian and Chinese. The interface itself is available in ten languages.

## High availability

- Run **two or more nodes on one PostgreSQL database** with `UCM_HA=1`, on Docker, Docker Compose, DEB and RPM packages, or the Helm chart's `ha.enabled`.
- **Shared state.** One elected node runs the scheduled tasks, so scheduled work runs once. Sessions, locks and real-time events are shared, and settings, encryption, the HTTPS certificate and Kerberos keytabs reach every node.
- **Backups and restores** work from any node.
- **Rolling package updates** on DEB and RPM: one node at a time, each from a verified download.
- **Health endpoints** report readiness, liveness and the leader, for load balancers and Kubernetes.
- Setup and limits: [docs/HA.md](https://github.com/NeySlim/ultimate-ca-manager/blob/v3.0/docs/HA.md).

## Policies and approvals everywhere

- **Approval on every enrollment protocol.** A policy that requires approval now holds ACME, EST, SCEP and WSTEP requests in the approval queue. Each client is told so in its own protocol's terms.
- **Revocations and renewals** can also be put under approval.
- **Algorithms come from profiles and CAs.** Allowed key types and signature hashes are carried by templates, profiles and CAs, and are enforced on every issuance path.
- **Unique subject per CA** is optional: a certificate whose subject another one already carries under that CA is refused.

## Windows and Active Directory

- **Windows enrollment profiles per realm**, each with its own CA, templates, Kerberos keytab, AD group and connector.
- **Several Active Directory connectors**, one per forest or domain.
- **A common name pattern** for Windows enrollment.
- **Renewal after a change of CA.**
- **Microsoft AD CS:** a pending request completes from UCM, and Kerberos works in the Docker images.

## Security

- **No default admin password.** The first password is provided or generated, and must be changed at first sign-in.
- **FIPS image on the OpenSSL FIPS Provider 3.5.9** (CMVP #5586). ML-DSA, Ed25519 and Ed448 are allowed where the module approves them, and blockers are reported at startup.
- **SSO:**
  - Microsoft Entra multi-tenant sign-in.
  - A test sign-in before enabling an OIDC or SAML provider.
  - One account opened by several providers.
  - A refused sign-in says what was read.
- **SSH CAs on an HSM key.** A restore never gives one HSM key to two authorities.

## Operations

- **Backups.** Archives are streamed and checked in chunks, so archives of any size are restored from the screen, with a report of what is left to do. Backups, restores and the audit chain check run in the background.
- **SQLite runs in WAL.** A write that meets another one waits briefly, then answers `503` with `Retry-After`, instead of blocking the other requests.
- **Revocations.** A revocation UCM never published, made under a CA held without its key, can be lifted by an administrator. A valid certificate of such a CA is deleted without being revoked.
- **Distribution:**
  - A CycloneDX **SBOM** for every package and image.
  - The **Helm chart** published at `oci://ghcr.io/neyslim/charts/ucm`.
  - **Major version image tags** `3` and `3-fips`.

## Upgrading from 2.x

- **Start from 2.254.** UCM 3.0 upgrades a database last started by UCM **2.254**, nothing older. From an earlier 2.x, install 2.254 first and start it once. A database 2.254 has not started is refused before anything is written, and the DEB and RPM packages refuse to install over a UCM older than 2.254.
- **Docker asks first.** The image stops until `UCM_ACCEPT_MAJOR_UPGRADE=3` is set. The Helm chart sets it, and the packages do not ask.
- **Going back to 2.254.** A SQLite database is copied before the upgrade (`ucm.db.2.254-before-3.0`), so you can return to 2.254 if needed.
- **Clusters.** The move to 3.0 is a full stop: stop every node, upgrade each one, then start them.
- **Behaviour changes.** Several API behaviours change (long backups and restores answer `202`, ACME finalize failures, deleting a CA a setting names, and others). Read [UPGRADE.md](https://github.com/NeySlim/ultimate-ca-manager/blob/v3.0/UPGRADE.md#upgrading-to-v30) before you upgrade.
- **2.x maintenance.** An installed 2.254 keeps receiving security fixes as 2.254.N and offers 3.0 as an explicit upgrade, never an automatic one.
