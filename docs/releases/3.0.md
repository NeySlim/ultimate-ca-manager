UCM 3.0 Phare is a major release. The console is rebuilt from the ground up, UCM can now run as a high-availability cluster, and approvals, Windows enrollment and backups have been reworked. It upgrades an installation running UCM 2.254 (any 2.254.N): read **Upgrading from 2.x** below before you install it.

## A new console

- **New layout.** A top bar replaces the sidebar: the modules in four groups, up to three pinned modules, global search, notifications, help and the account menu. A status bar shows the version, the node in HA mode, the live connection, and what is pending or running.
- **Two themes, Atelier and Aurore**, each dark, light or following the system. Purple Night and Orange Sunset are removed; accounts set to them open in Atelier.
- **An Overview home page.** Four headline figures and nine cards: work queue with its actions, automation health, issuances by source, expiry horizon, compliance, revocation coverage, hierarchy, latest operations, authorities and HSM. Cards can be shown, hidden and reordered, and layouts are saved per user. Counters and chart bars open the certificate list filtered to exactly what they count.
- **An inspector on every list.** Objects open in a tabbed dock beside or under the list, several at a time, and stay open across pages. The address keeps them, so a reload or a shared link reopens the same view.
- **Detached windows and comparison.** A certificate, an authority or a request can open in its own window over the page. Certificates can now be compared two to four at a time, side by side, with the differences marked.
- **Search** that lists pages, actions and objects, a **comment** on each certificate, and a **session lock** on demand (Alt+Shift+L).
- **Languages.** Russian joins the interface, now in ten languages. The built-in help and the new full guide are written in English, French, Spanish, Russian and Chinese; the other languages now show the English help.

## High availability

- **New in 3.0: two or more nodes on one PostgreSQL database**, with `UCM_HA=1` on Docker, Docker Compose, the DEB and RPM packages, or the Helm chart (`ha.enabled`). A single instance stays the default.
- **Shared state.** One elected node runs the scheduled tasks, so scheduled work runs once. Sessions, locks and real-time events are shared, and a change of settings, of private-key encryption, of the HTTPS certificate or of a Kerberos keytab made on one node reaches every node.
- **Backups and restores** work from any node.
- **Rolling package updates** on DEB and RPM: one node at a time, each from a verified download.
- **Health endpoints** report readiness, liveness and the leader, for load balancers and Kubernetes.
- Setup and limits: [docs/HA.md](https://github.com/NeySlim/ultimate-ca-manager/blob/v3.0/docs/HA.md).

## Policies and approvals

- **Approval on every enrollment protocol.** A policy that requires approval now holds ACME, EST, SCEP and WSTEP requests in the approval queue, and each client is told so in its own protocol's terms.
- **One key and hash default everywhere.** A request that names no key or hash gets the same default on every issuance path: RSA-2048 with SHA-256, or the first type the policies and the CA's compliance profile accept. The hash follows the signing key.
- **Optional unique subject per CA.** Switched on for a CA, it refuses a certificate whose subject another entity already holds under that CA. It is off by default, on upgraded CAs too.

## Windows and Active Directory

- **Windows enrollment profiles per realm**, each with its own CA, templates, Kerberos keytab, AD group and connector.
- **Several Active Directory connectors**, one per forest or domain.
- **A common name pattern** for Windows enrollment.
- **Renewal after a change of CA.** Certificates of a profile's former issuing CA keep renewing after the profile moves to another CA.
- **Microsoft AD CS.** A request left pending on the Windows CA is completed from UCM once approved there, and Kerberos authentication to AD CS now works in the Docker images.

## Security

- **No default admin password.** A new installation no longer creates `admin` / `changeme123`: you provide the first password, or UCM generates one that must be changed at first sign-in. Existing installations keep their administrator and password.
- **FIPS image on the OpenSSL FIPS Provider 3.5.9** (CMVP #5586). ML-DSA, Ed25519 and Ed448 are allowed where the module approves them, and whatever blocks FIPS operation is logged at every start.
- **SSO:**
  - Microsoft Entra multi-tenant sign-in.
  - A test sign-in before enabling an OIDC or SAML provider.
  - One account can sign in through several providers.
  - When a sign-in is refused for lack of a role, the audit log lists the groups that were read and where they came from.
- **SSH CAs on an HSM key.** An HSM key backs one authority only, and a restore that would give one key to two authorities is refused.

## Operations

- **Backups.** Archives are streamed and checked in chunks, so large archives are restored from the screen, where the picker stopped at 10 MB, with a report of what is left to do. Backups, restores and the audit chain check run in the background.
- **SQLite runs in WAL mode.** A write that meets another one waits up to 5 seconds, then answers `503` with `Retry-After`, instead of blocking the other requests.
- **Revocations.** For a CA that UCM holds without its key and does not sign for (no delegated OCSP responder, no external CRL), a revocation is never published: an administrator can lift it, and a valid certificate of such a CA can be deleted without being revoked first.
- **Distribution:**
  - A CycloneDX **SBOM** for every package and image.
  - The **Helm chart** published at `oci://ghcr.io/neyslim/charts/ucm`.
  - **Major version image tags** `3` and `3-fips`.

## Upgrading from 2.x

- **Start from 2.254.** UCM 3.0 upgrades a database last started by UCM **2.254**, nothing older. From an earlier 2.x, install 2.254 first and start it once. A database that 2.254 has never started is refused before anything is written, and the DEB and RPM packages refuse to install over a UCM older than 2.254.
- **Docker asks first.** The `latest` tag now points to 3.0. Started on a 2.254 database, the image stops without changing anything until `UCM_ACCEPT_MAJOR_UPGRADE=3` is set; to stay on 2.x, use the tag `2`. The Helm chart sets the variable, and the DEB and RPM packages do not ask.
- **Back up first.** A SQLite database is copied before the upgrade (`ucm.db.2.254-before-3.0`): that copy is the way back to 2.254. A PostgreSQL database is not copied: run `pg_dump` first. Keep a backup archive taken by 2.254 too, since 2.254 cannot read the archives 3.0 writes.
- **Approval policies now hold protocol requests.** In 2.x a policy that requires approval did not hold ACME, EST, SCEP and WSTEP requests; 3.0 holds them until an approver decides. Review these policies and their approvers before you upgrade.
- **Scripts and API clients.** the `serial_number` of a certificate or revocation record is always returned in decimal, the Windows enrollment settings become profiles (the `/xcep/config`, `/wstep/config`, `/kerberos/config` and `/ad-connector` routes are replaced), long backups and restores answer `202` with a job to follow, and on PostgreSQL without Redis everyone signs in again once. Read [UPGRADE.md](https://github.com/NeySlim/ultimate-ca-manager/blob/v3.0/UPGRADE.md#upgrading-to-v30) before you upgrade.
- **Automatic updates.** UCM 2.254.2 and later never install 3.0 by themselves: the Updates page offers it as a separate, explicit upgrade. UCM 2.254 and 2.254.1 see 3.0 as an ordinary update and install it when unattended install is on: update to the latest 2.254.N first, or turn unattended install off.
- **2.x maintenance.** UCM 2.254 keeps receiving security fixes, published as 2.254.N.
