**Ultimate Certificate Manager (UCM)** - це вебплатформа для керування центрами сертифікації з підтримкою PKI-протоколів (ACME, SCEP, EST, OCSP, CRL/CDP), інтеграцією з Microsoft ADCS, багатофакторною автентифікацією та керуванням життєвим циклом сертифікатів.

> **UCM - молодий проєкт, який активно розвивається.** Відгуки, повідомлення про помилки та побажання щодо функцій дуже вітаються! Сміливо [створюйте issue](https://github.com/NeySlim/ultimate-ca-manager/issues): кожне повідомлення допомагає зробити UCM кращим.

> Що нового, дивіться в [примітках до останнього випуску](https://github.com/NeySlim/ultimate-ca-manager/releases/latest) та в повному [CHANGELOG](CHANGELOG.md).

## Можливості

### Ядро PKI
- **Керування ЦС** -- кореневі та проміжні ЦС, подання ієрархії, імпорт і експорт, **відкликання проміжного ЦС** (через CRL і OCSP батьківського ЦС, нижче показується статус «відкликано вище»), **ЦС лише із сертифікатом** (ЦС, підписаний за зовнішнім запитом, закритий ключ якого імпортується пізніше), **ключі підпису в HSM** (закритий ключ ніколи не залишає HSM), **настроюваний профіль RFC 5280** (дайджест підпису, Key Usage, EKU), ЦС можна **приховати з форм випуску** (корінь, що підписує лише проміжні ЦС) зі стандартними значеннями в стилі Let's Encrypt і необов'язковою схемою підпису **RSA-PSS**, **профілі відповідності** за ANSSI, BSI та погодженими механізмами ЄС, **ЦС із зовнішнім підписом** (UCM створює пару ключів і CSR типу ЦС, офлайн- або зовнішній корінь підписує його: закритий ключ ніколи не залишає UCM, поновлення CSR з тим самим ключем), **перехресно підписані сертифікати ЦС** (додати або перехресно підписати поруч із власним сертифікатом ЦС, видавати в ланцюжку за замовчуванням під час заміни кореня, обирати ланцюжок для кожного експорту чи розгортання, бачити, що ще веде до старого кореня), **обмеження імен RFC 5280** під час створення (дозволені та виключені піддерева DNS, діапазонів IP і e-mail, застосовуються на кожному шляху випуску), строк дії від 1 року або будь-яка кількість днів до 50 років, а також необов'язкове правило **унікального суб'єкта** (сертифікат, суб'єкт якого вже має інша сутність під цим ЦС, відхиляється на кожному шляху випуску, RFC 5280 §4.1.2.6)
- **Життєвий цикл сертифікатів** -- випуск, підписання, відкликання (з причиною за RFC 5280, з кожного діалогу відкликання та масово), поновлення (**на місці**: ідентифікатори стабільні між поновленнями, замінені серійні номери залишаються в CRL/OCSP до початкового завершення строку дії, а вибраний строк дії все одно обмежується policy), перейменування (змінна відображувана назва, охоплює сертифікати без CN), експорт (PEM, DER, PKCS#12 з режимом сумісності 3DES/SHA-1 для Android 15 і старіших, macOS 14 і старіших, старих Windows та Java, JKS; ланцюжок за замовчуванням не містить самопідписаного кореня, а параметр **Include Root CA** додає його там, де цього потребує пакування чи імпорт), масові операції, фільтрація за статусом / видавцем / джерелом (ACME, SCEP, EST, AD CS, імпорт…), зокрема записи, **архівовані** поновленням або повторною реєстрацією та збережені для історії
- **Лінтинг відповідності** -- перевірки кожного сертифіката на відповідність RFC 5280, CA/Browser Forum Baseline Requirements та ETSI EN 319 412 за допомогою pkilint (і zlint, якщо доступний), лише довідково
- **Керування CSR** -- створення, імпорт і підписання запитів на підпис сертифіката з **власними Extra EKU OID** (RFC 5280 §4.2.1.12), **типізованою перевіркою SAN** (DNS / IP / Email / URI / UPN), кривими NIST P-256 / P-384 / P-521 та Brainpool P256r1 / P384r1 / P512r1 і **шляхом повернення із зовнішнього ЦС**: сертифікат, виданий деінде за CSR, створеним в UCM, під час імпорту завершує цей CSR і зберігає його закритий ключ; **імена, додані під час підписання** (адреса e-mail запиту S/MIME зі смарткартки, що містить лише CN, за тими самими обмеженнями імен, policy та погодженням) і **повторне підписання** з історії для пристроїв, які не можуть створити запит удруге
- **Шаблони сертифікатів** -- готові профілі для сервера, клієнта, підпису коду, e-mail, входу зі смарткарткою Windows; типи ключів RSA-2048/3072/4096, EC P-256/P-384/P-521, Brainpool і **постквантовий ML-DSA-44/65/87** (Ed25519/Ed448 для ЦС), **власні розширення X.509 за OID**, **qcStatements (ETSI EN 319 412-5) і OID policy сертифіката**, а також типові значення суб'єкта (разом з e-mail), що підставляються у форму випуску; експорт і імпорт JSON зі збереженням усіх параметрів, один шаблон або кілька в одному файлі
- **Виявлення сертифікатів** -- сканування мережі, профілі сканування, сканування за розкладом, імпорт сертифікатів
- **Сховище довіри** -- керування довіреними кореневими сертифікатами ЦС зі сповіщеннями про завершення строку дії та масовим видаленням
- **Відновлення ланцюжків** -- перевірка ланцюжків за AKI/SKI з планувальником автоматичного відновлення
- **SSH-сертифікати** -- керування ЦС SSH, підписання сертифікатів хостів і користувачів, імпорт ЦС і сертифікатів, зручні для curl скрипти налаштування; ідентифікатори ключів задає ЦС (`principals@назва ЦС`) або залишає запитувачу

### Протоколи
- **ACME** -- RFC 8555, автоматична реєстрація, автоматичне поновлення, виклики DNS-01/HTTP-01/TLS-ALPN-01, підтримка wildcard, **ідентифікатори IP (RFC 8738)**, **перевірка CAA із прив'язкою до облікового запису та методу (RFC 8657/8659)**, **External Account Binding (EAB, RFC 8555 §7.3.4)**, **Renewal Information (ARI, RFC 9773)**, **файли виклику HTTP-01, які віддає UCM** (переспрямуйте `/.well-known/acme-challenge/` з порту 80, перевіряються перед надсиланням, поновлюються автоматично), **вибір резолвера DNS-01** (автоматично, лише системний або лише перелічені резолвери, для мереж без доступу до публічних резолверів) для split-horizon, ACME на внутрішніх і приватних IP (зокрема необов'язковий loopback-upstream для ЦС на тому самому хості), **керування кількома ЦС** (вибір ЦС для кожного запиту, закріплений в замовленні, щоб поновлення використовували той самий ЦС: Let's Encrypt, Actalis, ZeroSSL, Google Trust Services, HARICA…), **зовнішній CSR і повторне використання ключа поновлення**, **попередній пробний прогін на staging**, **проксі для кількох ЦС** (попередньо перевірені upstream-домени проходять наскрізь, окремі кінцеві точки для кожного ЦС за адресою `/acme/proxy/<slug>/directory`, зокрема upstream-відкликання), **бажаний ланцюжок сертифікатів** (альтернативи RFC 8555 §7.4.2, для кожного облікового запису ЦС), **профілі сертифікатів** (draft-ietf-acme-profiles: іменовані policy випуску, оголошені в directory і доступні для вибору в кожному замовленні, кожна може бути прив'язана до шаблону сертифіката, чиї key usage та EKU тоді керують виданим сертифікатом, плюс **профіль за замовчуванням** і дайджест підпису за замовчуванням для замовлень, що не називають жодного), **керування локальними замовленнями сервера** (перегляд замовлень з очищенням і запланованим видаленням прострочених замовлень); проксі також публікує клієнтські значення TXT для dns-01, тож клієнтські попередні перевірки поширення (lego, Traefik, Caddy) проходять без змін, і повторно використовує ще не завершене замовлення облікового запису під час повторних спроб, а необов'язковий **слухач DNS UPDATE (RFC 2136)** дає змогу стандартним rfc2136-солверам, як-от у cert-manager, відповідати на DNS-01 через проксі з окремими ключами TSIG для кожного облікового запису
- **SCEP** -- автоматична реєстрація пристроїв за RFC 8894 з процесами погодження, GetCert/GetCRL, підписаний GetNextCACert, за потреби на звичайному HTTP-порту для клієнтів на кшталт sscep (поза режимом FIPS, який приймає лише транспорт ключа RSA-OAEP), поновлення, автентифіковані сертифікатом пристрою, шифрування AES-128 з резервним варіантом на паролі (PBKDF2) для клієнтів не на RSA; запит, погоджений вручну, видається за шаблоном профілю, через який він надійшов, точно так само, як і за автопогодження; іменовані профілі перевіряють виклики **Microsoft Intune** через Intune API орендаря, і через них реєструються пристрої Windows (транспорт ключа RSAES-OAEP) та Apple, див. [docs/integrations/intune-scep.md](docs/integrations/intune-scep.md)
- **EST** -- RFC 7030 Enrollment over Secure Transport, зокрема генерація ключа на сервері (CMS §4.4) і **мітки ЦС** (§3.2.2: кілька ЦС з однієї кінцевої точки)
- **OCSP** -- RFC 6960, статус сертифіката в реальному часі, запити з кількома сертифікатами, підтримка nonce, перевірка делегованого респондера з автоматичним поновленням його сертифіката, настроюваний строк дії відповіді
- **TSA (RFC 3161)** -- служба позначок часу з настроюваним policy OID; підписує **окремим кінцевим сертифікатом підпису** (RFC 3161, обов'язковим за замовчуванням і для суворих верифікаторів, як-от `openssl ts -verify` і jarsigner), який обирається серед виданих сертифікатів або створюється одним кліком (критичний, виняткове EKU timeStamping); поновлення відстежуються автоматично, ланцюжок видавця вбудовується в токени, суворий режим окремого підписувача, стан і строк дії підписувача виводяться на панель
- **CRL/CDP** -- розповсюдження списків відкликаних сертифікатів з підтримкою Delta CRL (RFC 5280 §5.2.4), розклад для кожного ЦС (строк дії відокремлений від частоти публікації) і настроюваним дайджестом підпису, необов'язкові іменовані URL (slug назви ЦС у шляхах CDP/AIA, можна ввімкнути для наявних ЦС), **завантаження CRL із зовнішнім підписом для офлайн-ЦС і ЦС без ключа** (перевіряється за сертифікатом ЦС із монотонністю номера CRL, віддається на наявній кінцевій точці CDP і береться до уваги OCSP)
- **AIA CA Issuers** -- завантаження сертифіката ЦС через Authority Information Access (RFC 5280 §4.2.2.1)

### Інтеграції
- **Microsoft ADCS** -- повний життєвий цикл через AD CS: підписання CSR, виявлення шаблонів, EOBO (Enroll On Behalf Of), поновлення і відкликання через конектор, а також необов'язковий адміністративний канал WinRM для синхронізації відкликань CRL, імпорту інвентарю ЦС і погодження чи відхилення запитів у черзі з панеллю стану ЦС
- **Автореєстрація Windows і конектор Active Directory** -- policy та реєстрація MS-XCEP/WSTEP для комп'ютерів і користувачів домену за шаблоном, названим у запиті; у прив'язці Kerberos шаблони для комп'ютерів і похідні від AD беруть суб'єкта з Active Directory (DNS-ім'я комп'ютера або DN і UPN користувача), через кілька контролерів домену з перемиканням і запланованою перевіркою стану кожного, ніколи з анонімним bind; реєстрація настроюється в **профілях для кожного realm** (`/api/v2/windows-profiles`), кожен із власним ЦС, шаблонами, keytab Kerberos, групою AD і конектором, а запит Kerberos обслуговує увімкнений профіль realm його принципала (прив'язку UsernamePassword обслуговує профіль за замовчуванням, коли він увімкнений, поновлення за сертифікатом обслуговує профіль, записаний у пред'явленому сертифікаті), через **кілька конекторів Active Directory** (по одному на ліс або домен)
- **Microsoft Intune** -- перевірка викликів SCEP для пристроїв під керуванням Intune, реєстрації застосунків Entra визначаються один раз у SCEP › Intune app registrations і вибираються для кожного профілю, з покроковим посібником у `docs/integrations/intune-scep.md`
- **HSM** -- SoftHSM у комплекті, PKCS#11, Azure Key Vault, Google Cloud KMS, OpenBao/Vault Transit; **ЦС у HSM** з непереносними ключами підпису, RSA-PSS і Brainpool на PKCS#11 та заявленою сертифікацією пристрою (Common Criteria, EUCC, FIPS 140-3), яку перевіряє профіль відповідності ЄС; перевірка з'єднання показує, що повідомляє модуль PKCS#11 (бібліотека, виробник, прошивка)
- **Kubernetes / cert-manager** -- еталонні маніфести ClusterIssuer (HTTP-01 + DNS-01 з EAB), приклад Certificate, шаблон Secret у `examples/kubernetes/cert-manager/`
- **DNS-провайдери** -- Cloudflare, Route53, Azure DNS, Plesk та інші для викликів ACME DNS-01
- **Вебхуки** -- сповіщення за подіями життєвого циклу сертифікатів (понад 15 типів подій), **історія доставки для кожної кінцевої точки з ручним повтором**, довговічна асинхронна черга доставки з експоненційним збільшенням затримки та вікно зберігання історії, щоб вона не росла безкінечно

### Безпека та доступ
- **Автентифікація** -- пароль, WebAuthn/FIDO2 (також як другий фактор, поряд із TOTP або замість нього), 2FA TOTP, mTLS, ключі API (`X-API-Key` або `Authorization: Bearer`)
- **SSO** -- LDAP (LDAPS або StartTLS), OAuth2 (Azure/Google/GitHub), єдиний вхід SAML з Single Logout, зіставлення ролей із вбудованими та **власними ролями** (групи SAML зчитуються із затвердження, зокрема claims Entra ID та AD FS) і настроюваний формат NameID; **відстеження `auth_source` для кожного користувача** та необов'язкова синхронізація ролей під час входу
- **RBAC** -- 4 вбудовані ролі (Admin, Operator, Auditor, Viewer) плюс власні ролі з докладними дозволами; **групи надають додаткові дозволи** понад роль користувача (ніколи не адміністратора)
- **Policy та погодження** -- policy випуску сертифікатів з процесами погодження та обов'язковими правилами (дозволені типи ключів і хеші підпису, ліміт DNS SAN, ліміт строку дії, з областю за ЦС, шаблоном або DNS-шаблоном), що охоплюють **кожен шлях оператора** (форма випуску, підписання збереженого запиту окремо чи масово та поновлення) і, для типів ключів та хешів, також ACME, SCEP, EST, WSTEP і створення ЦС; policy, що вимагає погодження, утримує **запити ACME, EST, SCEP і WSTEP** у черзі погодження, і кожен клієнт отримує про це відповідь мовою свого протоколу (ACME `processing`, EST 202 з Retry-After, SCEP PENDING, WSTEP pending); policy також може поставити під погодження **відкликання та поновлення**; запит у черзі закривається сам, якщо його ціль тим часом підписано, поновлено, видалено чи відкликано
- **Типові значення ключів і хешів** -- запит, що не називає ключ чи хеш, на кожному шляху випуску дотримується одного значення за замовчуванням (RSA-2048 із SHA-256, якщо профіль або policy не відхиляє його, тоді перший прийнятний тип), хеш відповідає ключу підпису, а новий проміжний ЦС ніколи не бере хеш слабший за батьківський
- **Журнали аудиту** -- журналювання дій із перевіркою цілісності, віддалене пересилання через syslog і необов'язковий строк зберігання
- **Шифрування закритих ключів** -- AES-128 (Fernet, HMAC-SHA256) у спокої під головним ключем, створеним під час першого запуску (в контейнері, коли `/etc/ucm` є томом) або заданим як `KEY_ENCRYPTION_KEY`, що охоплює ключі ЦС і сертифікатів, ключі ЦС SSH і цілей розгортання, ключі облікових записів ACME та EAB, виклики SCEP і паролі bind LDAP, з функцією **Encrypt remaining keys** для секретів, збережених до ввімкнення шифрування; зі ввімкненим шифруванням на диску не зберігається жодного файла ключа у відкритому вигляді (наявні дзеркала видаляються під час ввімкнення та під час запуску, файли публічних сертифікатів залишаються), а файли ключів створюються заново, коли шифрування вимкнено
- **Висока доступність** -- запускайте два чи більше вузлів на одній базі PostgreSQL з `UCM_HA=1` (Docker, Docker Compose, DEB/RPM або `ha.enabled` у Helm chart): один обраний вузол виконує заплановані завдання, налаштування, шифрування, резервні копії та поступові оновлення доходять до кожного вузла, а сеанси спільні, тому прив'язки до адреси джерела потребують лише кінцеві точки реєстрації Kerberos (див. [docs/HA.md](docs/HA.md))
- **Режим FIPS** -- образ Docker `-fips` запускає криптографію UCM у OpenSSL FIPS Provider 3.5.9 (сертифікат CMVP #5586), який схвалює ML-DSA, Ed25519 і Ed448, тож постквантові підписи та підписи EdDSA доступні в режимі FIPS з образом; пакети DEB і RPM, зібрані з `UCM_FIPS_BUILD=1`, працюють на модулі FIPS у RHEL 9 (#5573) або Ubuntu 24.04 Pro (#5115), які їх не надають. З `UCM_FIPS=1` UCM запускається лише на активному модулі, що пройшов самоперевірку, створює ключі через нього, дозволяє алгоритм лише тоді, коли завантажений модуль його схвалює, а решту відхиляє (MD5, 3DES, scrypt, Argon2id, застарілий PKCS#12, NTLM), а перевірка готовності заздалегідь перелічує, що втратив би екземпляр. Сам UCM не є валідованим модулем, а Debian 13 та arm64 не входять до перевірених конфігурацій сертифіката #5586
- **Профілі відповідності** -- policy для кожного ЦС за ANSSI PG-083, BSI TR-02102-1 та погодженими криптографічними механізмами ECCG (типи ключів, хеші, схеми підпису, горизонти строку дії, ключі ЦС у HSM, підписувач позначок часу на EC), з відмовами там, де текст це вимагає, і попередженнями там, де рекомендує, із попередньою перевіркою лише для читання перед підключенням профілю до наявного ЦС; жоден із цих органів не сертифікував і не кваліфікував UCM
- **SBOM** -- SBOM у форматі CycloneDX для кожного пакета й платформи образу кожного випуску, прив'язаний до хеша файла чи дайджесту образу, що перелічує його вміст із версіями та заявленими ліцензіями й те, що пакет розв'язує під час встановлення ([docs/SBOM.md](docs/SBOM.md))
- **Посилення захисту** -- HSTS, що настроює оператор (Settings → Security або перевизначення через середовище), обмеження довірених проксі для заголовків клієнтського сертифіката, дозволи ключів API обмежені власними дозволами творця; довірені проксі можна задавати мережами CIDR, і після ввімкнення підтримки проксі заголовки `X-Forwarded-*` приймаються лише від них, тож клієнт, що звертається до бекенда напряму, не може підробити свою адресу; вебінтерфейс і API керування можна **обмежити переліком IP-адрес і мереж**, а кінцеві точки PKI-протоколів залишаються доступними

### Експлуатація та моніторинг
- **Огляд** -- чотири головні показники, кроки першого налаштування та дев'ять незалежних карток (черга роботи з діями поновлення, повтору та публікації, стан автоматизації, випуски за джерелами, горизонт завершення строку дії, відповідність, охоплення відкликанням, ієрархія, останні операції, центри та HSM), які показуються, приховуються та впорядковуються за допомогою пресетів розкладки, збережених для кожного користувача, і самі перезавантажуються, коли змінюються дані
- **Звіти** -- PDF-звіти за розкладом, зведення для керівництва, відкликані сертифікати, власні шаблони
- **Набір інструментів для сертифікатів** -- перевірка SSL, декодер CSR/сертифікатів, зіставлення ключів, конвертер форматів
- **Сповіщення e-mail** -- SMTP зі STARTTLS або неявним TLS (порт 465), **OAuth2 (XOAUTH2)** для Gmail, Outlook.com і Microsoft 365, настроювані шаблони HTML/текст, сповіщення про завершення строку дії сертифікатів з кількома порогами в днях (один e-mail на поріг і період дії, ескалація на кшталт 30/14/7/1), за потреби без сертифікатів, які клієнти ACME поновлюють самі
- **Хуки розгортання** -- передавання виданих і поновлених сертифікатів, а також відновлених CRL (DER або пакет PEM з CRL батьківських ЦС) на віддалені хости через SSH/SFTP, зі шляхами призначення та необов'язковою командою перезавантаження для кожної прив'язки: автентифікація за ключем (згенерований ed25519 або імпортований ключ, зашифрований у спокої), закріплення ключа хоста під час першого підключення, шляхи призначення для кожної прив'язки (сертифікат / ключ / повний ланцюжок, ланцюжок без самопідписаного кореня, якщо прив'язка його не вимагає, записується атомарно), довговічна черга доставки з повторами та історією кожної доставки, **пресет для того самого хоста** для служб, що працюють поруч з UCM, і **цілі HTTP API**, які передають сертифікат на міжмережевий екран, балансувальник навантаження чи хмарний API одним запитом, побудованим із шаблону тіла (URL, метод, зашифровані заголовки, змінні на кшталт `{{cert_pem|json}}`, закритий ключ лише за явної згоди через перевірений HTTPS)
- **Резервне копіювання й відновлення** -- ручні та заплановані зашифровані резервні копії з політиками зберігання та необов'язковим обмеженням місця, яке займають збережені архіви; архіви є потоками незалежно автентифікованих блоків, тож створення архіву та його перевірка перед відновленням не тримають його цілком у пам'яті; архіви містять замовлення клієнтів ACME та запити в черзі, відновлюються в режимі злиття чи заміни, зіставляють рядки за назвою між інсталяціями та повторно виконують міграції відновлення
- **Пакет діагностичних журналів** -- завантаження одним кліком (Settings → About → Diagnostic) журналів застосунку, журналу помилок, журналу systemd і діагностики системи без секретів у вигляді ZIP з приховуванням чутливих токенів
- **Перегляд системних журналів** -- перегляд журналів застосунку, доступу, помилок і journal systemd з інтерфейсу, з фільтрами за рівнем, часовим вікном і текстом та прихованими секретами
- **Метрики Prometheus** -- необов'язкова кінцева точка `/metrics` за bearer-токеном, що віддає лічильники сертифікатів, ЦС, планувальника, вебхуків і ACME
- **Планувальник** -- адміністративне подання фонових завдань (перевірки строку дії, оновлення CRL, доставка вебхуків, резервні копії, автоматичне поновлення) зі статусом і запуском за вимогою, що працює в окремому процесі під gunicorn
- **Самообслуговування по HTTPS** -- застосуйте будь-який виданий сертифікат до вебінтерфейсу; прив'язка автоматично слідує за поновленнями (файли створюються заново, службу перезапущено)
- **Безпечні мережеві налаштування за замовчуванням** -- прослуховування dual-stack (`HOST=::` обслуговує IPv6 та IPv4 на одному сокеті) і запобіжники адміністративної Base URL (перевірка досяжності перед застосуванням, канонічне переспрямування відступає, коли хост перестає розв'язуватися, перемикач відновлення `UCM_DISABLE_CANONICAL_REDIRECT=1`)
- **Оновлення програмного забезпечення** -- вбудована перевірка оновлень зі встановленням одним кліком, щоденна перевірка за розкладом у стабільному каналі або каналі кандидатів у випуск і необов'язкове встановлення без нагляду (DEB/RPM) з обов'язковою перевіркою SHA256 та достовірними подіями результату (встановлено лише після того, як фактичне встановлення підтверджено за версією), а також необов'язкове одноразове вікно приміток до випуску для кожного користувача після оновлення
- **Глобальний пошук** -- пошук за всіма ресурсами та палітра команд (Ctrl+K)

### Платформа
- **Теми** -- Atelier та Aurore, кожна темна або світла чи за системою; **налаштування кожного користувача зберігаються на сервері** (мова, тема, режим)
- **i18n** -- 10 мов (EN, FR, DE, ES, IT, PT, UK, RU, ZH, JA)
- **Збережений стан інтерфейсу** -- вибрані фільтри зберігаються між перезавантаженнями на головних сторінках зі списками (сертифікати, ЦС, шаблони, policy, журнали аудиту, сховище довіри, користувачі, SSH)
- **База даних** -- SQLite (за замовчуванням) або **рідний бекенд PostgreSQL** з двоспрямованим інтерфейсом міграції
- **Адаптивний інтерфейс** -- React 18 + Radix UI, зручний на мобільних пристроях
- **У реальному часі** -- оновлення через WebSocket: зміна, зроблена іншим оператором, оновлює списки, що її показують, а повторне підключення після збою перезавантажує їх, а не залишає застарілі рядки на екрані
- **Багато платформ** -- Docker, Debian/Ubuntu (.deb), RHEL/Rocky/Fedora (.rpm); пакети встановлюють ротацію журналів доступу та помилок
- **Готовність до зворотного проксі** -- публічні порти незалежні від портів прослуховування (явні `:80` або `:443` у базових URL оголошуються як введено), довірені проксі за IP чи мережею CIDR і значення `proxy.*` Helm chart для Ingress перед UCM

## Швидкий старт

### Docker

```bash
docker run -d --restart=unless-stopped \
  --name ucm \
  -p 8443:8443 \
  -p 8080:8080 \
  -v ucm-data:/opt/ucm/data \
  -v ucm-config:/etc/ucm \
  neyslim/ultimate-ca-manager:latest
```

Також доступний у GitHub Container Registry: `ghcr.io/neyslim/ultimate-ca-manager`. Варіант FIPS має тег `<version>-fips` (запускайте його з `UCM_FIPS=1`).

### Debian/Ubuntu

Завантажте пакет `.deb` з [останнього випуску](https://github.com/NeySlim/ultimate-ca-manager/releases/latest):

```bash
sudo dpkg -i ucm_<version>_all.deb
sudo systemctl enable --now ucm
```

### RHEL/Rocky/Fedora

Завантажте пакет `.rpm` з [останнього випуску](https://github.com/NeySlim/ultimate-ca-manager/releases/latest): `ucm-VERSION-1.fc43.noarch.rpm` для Fedora, `ucm-el9-VERSION-1.el9.noarch.rpm` для RHEL, Rocky Linux та AlmaLinux 9, `ucm-el10-VERSION-1.el10.noarch.rpm` для тих самих дистрибутивів версії 10.

```bash
sudo dnf install ./ucm-VERSION-1.fc43.noarch.rpm
sudo systemctl enable --now ucm
```

**Доступ:** `https://localhost:8443` або `https://your-server-fqdn:8443`
**Перший вхід:** `admin` з паролем, згенерованим під час першого запуску: `sudo cat /opt/ucm/data/initial-admin-password` (Docker: `docker exec <container> cat /opt/ucm/data/initial-admin-password`). Його потрібно змінити під час першого входу. Щоб задати власний, див. [First access](docs/installation/README.md#first-access).

Усі способи, зокрема Docker Compose та встановлення з вихідного коду, описано в [Installation Guide](docs/installation/README.md).
