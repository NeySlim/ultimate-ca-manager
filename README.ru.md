**Ultimate Certificate Manager (UCM)** это веб-платформа для управления центрами сертификации с поддержкой PKI-протоколов (ACME, SCEP, EST, OCSP, CRL/CDP), интеграцией с Microsoft ADCS, многофакторной аутентификацией и управлением жизненным циклом сертификатов.

> **UCM: молодой и активно развивающийся проект.** Отзывы, сообщения об ошибках и пожелания будут очень кстати! Не стесняйтесь [создавать issue](https://github.com/NeySlim/ultimate-ca-manager/issues): каждое сообщение помогает сделать UCM лучше.

> Что нового, смотрите в [заметках к последнему выпуску](https://github.com/NeySlim/ultimate-ca-manager/releases/latest) и в полном [CHANGELOG](CHANGELOG.md).

## Возможности

### Ядро PKI
- **Управление ЦС** -- корневые и промежуточные ЦС, иерархическое представление, импорт/экспорт, **отзыв промежуточных ЦС** (CRL и OCSP родительского ЦС, статус «отозван вышестоящим» ниже по цепочке), **ЦС только с сертификатом** (ЦС, подписанный по внешнему запросу, закрытый ключ которого импортируется позже), **ключи подписи в HSM** (закрытый ключ никогда не покидает HSM), **настраиваемый профиль RFC 5280** (хеш подписи, Key Usage, EKU), ЦС можно **скрыть из форм выпуска** (корневой ЦС, подписывающий только промежуточные) со значениями по умолчанию как у Let's Encrypt и необязательной схемой подписи **RSA-PSS**, **профили соответствия** требованиям ANSSI, BSI и согласованным механизмам ЕС, **ЦС с внешней подписью** (UCM создаёт пару ключей и CSR типа CA, автономный/внешний корневой ЦС подписывает его: закрытый ключ не покидает UCM, продление по CSR с тем же ключом), **кросс-подписанные сертификаты ЦС** (прикрепить или выполнить кросс-подпись рядом с собственным сертификатом ЦС, отдавать его в цепочке по умолчанию при смене корня, выбирать цепочку при экспорте или развёртывании, видеть, что всё ещё строится к старому корню), **ограничения имён RFC 5280**, задаваемые при создании (разрешённые и исключённые поддеревья DNS, диапазонов IP и e-mail, применяются на всех путях выпуска), срок действия от 1 года или любое число дней до 50 лет и необязательное правило **уникального субъекта** (сертификат, субъект которого уже принадлежит другому объекту в этом ЦС, отклоняется на всех путях выпуска, RFC 5280 §4.1.2.6)
- **Жизненный цикл сертификатов** -- выпуск, подпись, отзыв (с причиной по RFC 5280, из любого диалога отзыва и массово), продление (**на месте**: идентификаторы сохраняются при продлении, заменённые серийные номера остаются в CRL/OCSP до исходного срока истечения, выбранный срок действия по-прежнему ограничен политикой), переименование (изменяемое отображаемое имя, подходит и для сертификатов без CN), экспорт (PEM, DER, PKCS#12 с режимом совместимости 3DES/SHA-1 для Android 15 и старше, macOS 14 и старше, старых Windows и Java, JKS; цепочка по умолчанию не содержит самоподписанный корень, но есть параметр **Include Root CA** для случаев, когда он нужен для упаковки или импорта), массовые операции, фильтрация по статусу / издателю / источнику (ACME, SCEP, EST, AD CS, импорт…), включая записи, **архивированные** при продлении или повторной регистрации и сохранённые для истории
- **Проверка соответствия (linting)** -- проверки каждого сертификата на соответствие RFC 5280, CA/Browser Forum Baseline Requirements и ETSI EN 319 412 с помощью pkilint (и zlint, если доступен), только для информации
- **Управление CSR** -- создание, импорт и подпись запросов на сертификат с **пользовательскими OID Extra EKU** (RFC 5280 §4.2.1.12), **типизированной проверкой SAN** (DNS / IP / Email / URI / UPN), кривыми NIST P-256 / P-384 / P-521 и Brainpool P256r1 / P384r1 / P512r1 и **путём возврата из внешнего ЦС**: сертификат, выпущенный в другом месте по CSR, созданному в UCM, при импорте закрывает этот CSR и сохраняет его закрытый ключ; **имена, добавляемые при подписи** (адрес e-mail в S/MIME-запросе от смарт-карты, содержащем только CN, с теми же ограничениями имён, политиками и согласованием) и **повторная подпись** из истории для устройств, не способных сформировать запрос дважды
- **Шаблоны сертификатов** -- готовые профили для сервера, клиента, подписи кода, e-mail, входа по смарт-карте Windows; типы ключей RSA-2048/3072/4096, EC P-256/P-384/P-521, Brainpool и **постквантовые ML-DSA-44/65/87** (Ed25519/Ed448 для ЦС), **пользовательские расширения X.509 по OID**, **qcStatements (ETSI EN 319 412-5) и OID политик сертификата**, значения субъекта по умолчанию (включая e-mail), подставляемые в форму выпуска; экспорт и импорт в JSON с сохранением всех параметров, один шаблон или несколько в файле
- **Обнаружение сертификатов** -- сканирование сети, профили сканирования, сканирование по расписанию, импорт сертификатов
- **Хранилище доверия** -- управление доверенными корневыми сертификатами с оповещениями об истечении и массовым удалением
- **Восстановление цепочек** -- проверка цепочек по AKI/SKI с планировщиком автоматического восстановления
- **SSH-сертификаты** -- управление SSH-центром сертификации, подпись сертификатов хостов и пользователей, импорт ЦС и сертификатов, скрипты настройки, удобные для curl; идентификаторы ключей задаёт ЦС (`principals@имя ЦС`) или запрашивающая сторона

### Протоколы
- **ACME** -- RFC 8555, автоматическая регистрация и продление, проверки DNS-01/HTTP-01/TLS-ALPN-01, wildcard, **IP-идентификаторы (RFC 8738)**, **проверка CAA с привязкой к аккаунту и методу (RFC 8657/8659)**, **External Account Binding (EAB, RFC 8555 §7.3.4)**, **Renewal Information (ARI, RFC 9773)**, **файлы HTTP-01, отдаваемые самим UCM** (перенаправляйте `/.well-known/acme-challenge/` с порта 80, проверка перед отправкой, автоматическое продление), **выбор DNS-преобразователя для DNS-01** (автоматически, только системный или только перечисленные, для сетей без доступа к публичным преобразователям) для split-horizon, ACME на внутренних/частных IP (включая необязательный loopback-upstream для ЦС на том же хосте), **управление несколькими ЦС** (выбор ЦС в каждом запросе, закрепляется за заказом, так что продления используют тот же ЦС: Let's Encrypt, Actalis, ZeroSSL, Google Trust Services, HARICA…), **внешний CSR и повторное использование ключа при продлении**, **пробный прогон в staging**, **прокси для нескольких ЦС** (заранее проверенные upstream-домены проходят напрямую, отдельные точки входа для ЦС по адресу `/acme/proxy/<slug>/directory`, включая отзыв в upstream), **предпочтительная цепочка сертификатов** (альтернативы по RFC 8555 §7.4.2, для каждого аккаунта ЦС), **профили сертификатов** (draft-ietf-acme-profiles: именованные политики выпуска, объявляемые в directory и выбираемые для каждого заказа, каждая при желании связана с шаблоном сертификата, чьи key usage и EKU определяют выпущенный сертификат, плюс **профиль по умолчанию** и хеш подписи по умолчанию для заказов без профиля), **управление локальными заказами сервера** (список заказов с очисткой и плановым удалением истёкших); прокси также публикует клиентские значения TXT для dns-01, чтобы проверки распространения на стороне клиента (lego, Traefik, Caddy) проходили без изменений, повторно использует ещё не завершённый заказ аккаунта при повторных попытках, а необязательный **DNS UPDATE-слушатель (RFC 2136)** позволяет стандартным rfc2136-решателям, например cert-manager, проходить DNS-01 через прокси с отдельными ключами TSIG для каждого аккаунта
- **SCEP** -- автоматическая регистрация устройств по RFC 8894 с процессами согласования, GetCert/GetCRL, подписанный GetNextCACert, при необходимости на обычном HTTP-порту для клиентов вроде sscep (вне режима FIPS, где допускается только транспорт ключа RSA-OAEP), продления с аутентификацией по сертификату устройства, шифрование AES-128 с запасным вариантом на основе пароля (PBKDF2) для клиентов не на RSA; запрос, одобренный вручную, выпускается по шаблону профиля, через который он пришёл, точно так же, как при автоматическом одобрении; именованные профили проверяют challenge **Microsoft Intune** через API Intune арендатора, через них регистрируются устройства Windows (транспорт ключа RSAES-OAEP) и Apple, см. [docs/integrations/intune-scep.md](docs/integrations/intune-scep.md)
- **EST** -- RFC 7030 Enrollment over Secure Transport, включая генерацию ключа на сервере (CMS §4.4) и **метки ЦС** (§3.2.2: несколько ЦС на одной точке входа)
- **OCSP** -- RFC 6960, состояние сертификатов в реальном времени, запросы по нескольким сертификатам, поддержка nonce, проверка делегированного ответчика с автоматическим продлением его сертификата, настраиваемый срок действия ответа
- **TSA (RFC 3161)** -- служба меток времени с настраиваемым OID политики; подписывает **выделенным конечным сертификатом подписи** (RFC 3161, обязателен по умолчанию и для строгих проверяющих, таких как `openssl ts -verify` и jarsigner), выбранным из выпущенных сертификатов или созданным в один клик (критичный, исключительный EKU timeStamping); продления отслеживаются автоматически, цепочка издателя встраивается в токены, есть строгий режим выделенного подписанта, состояние и срок действия подписанта выводятся на панели
- **CRL/CDP** -- распространение списков отозванных сертификатов с поддержкой Delta CRL (RFC 5280 §5.2.4), расписание для каждого ЦС (срок действия не зависит от периодичности публикации) и настраиваемый хеш подписи, необязательные именованные URL (слаг имени ЦС в путях CDP/AIA, включается и для существующих ЦС), **загрузка CRL, подписанных извне, для автономных ЦС и ЦС без ключа** (проверяется по сертификату ЦС с контролем монотонности номера CRL, отдаётся по существующему адресу CDP и учитывается OCSP)
- **AIA CA Issuers** -- загрузка сертификата ЦС через Authority Information Access (RFC 5280 §4.2.2.1)

### Интеграции
- **Microsoft ADCS** -- полный жизненный цикл через AD CS: подпись CSR, обнаружение шаблонов, EOBO (Enroll On Behalf Of), продление и отзыв через коннектор, а также необязательный административный канал WinRM для синхронизации отзыва CRL, импорта инвентаря ЦС, одобрения/отклонения ожидающих запросов и панель состояния ЦС
- **Автоматическая регистрация Windows и Active Directory Connector** -- политика и регистрация MS-XCEP/WSTEP для компьютеров и пользователей домена по шаблону, указанному в запросе; при привязке Kerberos шаблоны для компьютеров и на основе AD берут субъект из Active Directory (DNS-имя компьютера либо DN и UPN пользователя), с несколькими контроллерами домена, переключением при отказе и плановой проверкой состояния каждого DC, без анонимного bind; регистрация настраивается в **профилях для каждого realm** (`/api/v2/windows-profiles`), у каждого свои ЦС, шаблоны, keytab Kerberos, группа AD и коннектор; запрос Kerberos обслуживается включённым профилем realm его участника (привязка UsernamePassword -- профилем по умолчанию, если он включён, продление по сертификату -- профилем, записанным в предъявленном сертификате), с **несколькими коннекторами Active Directory** (по одному на лес или домен)
- **Microsoft Intune** -- проверка SCEP challenge для устройств под управлением Intune, регистрации приложений Entra задаются один раз в разделе SCEP › Intune app registrations и выбираются для каждого профиля, пошаговое руководство в `docs/integrations/intune-scep.md`
- **HSM** -- SoftHSM в комплекте, PKCS#11, Azure Key Vault, Google Cloud KMS, OpenBao/Vault Transit; **ЦС в HSM** с неэкспортируемыми ключами подписи, RSA-PSS и Brainpool на PKCS#11 и заявленная сертификация устройства (Common Criteria, EUCC, FIPS 140-3), проверяемая профилем соответствия ЕС; проверка соединения показывает, что сообщает модуль PKCS#11 (библиотека, производитель, прошивка)
- **Kubernetes / cert-manager** -- эталонные манифесты ClusterIssuer (HTTP-01 + DNS-01 с EAB), пример Certificate, шаблон Secret в `examples/kubernetes/cert-manager/`
- **DNS-провайдеры** -- Cloudflare, Route53, Azure DNS, Plesk и другие для проверок ACME DNS-01
- **Вебхуки** -- уведомления о событиях жизненного цикла сертификатов (более 15 типов событий), **история доставки по каждой точке с ручным повтором**, надёжная асинхронная очередь доставки с экспоненциальной задержкой и срок хранения истории, чтобы она не росла бесконечно

### Безопасность и доступ
- **Аутентификация** -- пароль, WebAuthn/FIDO2 (в том числе как второй фактор, наряду с TOTP или вместо него), 2FA по TOTP, mTLS, ключи API (`X-API-Key` или `Authorization: Bearer`)
- **SSO** -- LDAP (LDAPS или StartTLS), OAuth2 (Azure/Google/GitHub), единый вход SAML с Single Logout, сопоставление ролей со встроенными и **пользовательскими ролями** (группы SAML читаются из assertion, включая claims Entra ID и AD FS) и настраиваемый формат NameID; **учёт `auth_source` для каждого пользователя** и необязательная синхронизация ролей при входе
- **RBAC** -- 4 встроенные роли (Admin, Operator, Auditor, Viewer) и пользовательские роли с гранулярными правами; **группы дают дополнительные права** сверх роли пользователя (но никогда права администратора)
- **Политики и согласование** -- политики выпуска сертификатов с процессами согласования и обязательными правилами (допустимые типы ключей и хеши подписи, ограничение числа DNS SAN, ограничение срока действия, область действия по ЦС, шаблону или DNS-маске), охватывающие **каждый путь оператора** (форма выпуска, подпись сохранённого запроса по одному или массово, продление) и, для типов ключей и хешей, также ACME, SCEP, EST, WSTEP и создание ЦС; политика, требующая согласования, удерживает **запросы ACME, EST, SCEP и WSTEP** в очереди согласования, и каждый клиент узнаёт об этом на языке своего протокола (ACME `processing`, EST 202 с Retry-After, SCEP PENDING, WSTEP pending); политика может также ставить под согласование **отзывы и продления**; запрос в очереди закрывается сам, если его цель тем временем подписана, продлена, удалена или отозвана
- **Ключи и хеши по умолчанию** -- запрос, не указывающий ключ или хеш, получает единое значение по умолчанию на всех путях выпуска (RSA-2048 с SHA-256, если профиль или политика не запрещают, иначе первый разрешённый тип), хеш следует за ключом подписи, а новый промежуточный ЦС никогда не получает хеш слабее родительского
- **Журналы аудита** -- журналирование действий с проверкой целостности, пересылка в удалённый syslog и необязательный срок хранения
- **Шифрование закрытых ключей** -- AES-128 (Fernet, HMAC-SHA256) при хранении под мастер-ключом, создаваемым при первом запуске (в контейнере, если `/etc/ucm` является томом) или заданным в `KEY_ENCRYPTION_KEY`, охватывает ключи ЦС и сертификатов, ключи SSH CA и целей развёртывания, ключи аккаунтов ACME и EAB, SCEP challenge и пароли привязки LDAP, с функцией **Encrypt remaining keys** для секретов, сохранённых до включения шифрования; при включённом шифровании файлы ключей в открытом виде на диске не хранятся (существующие копии удаляются при включении и при запуске, файлы открытых сертификатов остаются), а при отключении файлы ключей создаются заново
- **Высокая доступность** -- два и более узла на одной базе PostgreSQL с `UCM_HA=1` (Docker, Docker Compose, DEB/RPM или `ha.enabled` в Helm-чарте): один выбранный узел выполняет плановые задачи, настройки, шифрование, резервные копии и плавные обновления распространяются на все узлы, сессии общие, поэтому привязка к адресу источника нужна только для точек регистрации Kerberos (см. [docs/HA.md](docs/HA.md))
- **Режим FIPS** -- образ Docker с суффиксом `-fips` выполняет криптографию UCM в OpenSSL FIPS Provider 3.5.9 (сертификат CMVP #5586), который одобряет ML-DSA, Ed25519 и Ed448, поэтому в этом образе постквантовые подписи и подписи EdDSA доступны в режиме FIPS; пакеты DEB и RPM, собранные с `UCM_FIPS_BUILD=1`, работают на модуле FIPS в RHEL 9 (#5573) или Ubuntu 24.04 Pro (#5115), которые их не предоставляют. При `UCM_FIPS=1` UCM запускается только на активном модуле, прошедшем самотестирование, генерирует ключи через него, разрешает алгоритм, только если загруженный модуль его одобряет, и отклоняет остальные (MD5, 3DES, scrypt, Argon2id, устаревший PKCS#12, NTLM), а проверка готовности заранее перечисляет, что экземпляр потеряет. Сам UCM не является валидированным модулем, а Debian 13 и arm64 не входят в проверенные конфигурации сертификата #5586
- **Профили соответствия** -- политики для каждого ЦС по ANSSI PG-083, BSI TR-02102-1 и согласованным ECCG криптографическим механизмам (типы ключей, хеши, схемы подписи, горизонты срока действия, ключи ЦС в HSM, подписант меток времени на EC), с отказами там, где текст предписывает, и предупреждениями там, где рекомендует, и предварительной проверкой только для чтения перед подключением профиля к существующему ЦС; UCM не сертифицирован и не квалифицирован ни одним из этих органов
- **SBOM** -- CycloneDX SBOM для каждого пакета и платформы образа в каждом выпуске, привязанный к хешу файла или дайджесту образа, с перечнем поставляемого с версиями и заявленными лицензиями и того, что пакет разрешает при установке ([docs/SBOM.md](docs/SBOM.md))
- **Усиление защиты** -- настраиваемый оператором HSTS (Settings → Security или переменная окружения), контроль доверенных прокси для заголовков клиентского сертификата, права ключей API ограничены правами их создателя; доверенные прокси можно задавать сетями CIDR, и после включения поддержки прокси заголовки `X-Forwarded-*` учитываются только от них, так что клиент, обращающийся к бэкенду напрямую, не может подделать свой адрес; веб-интерфейс и API управления можно **ограничить перечисленными IP-адресами и сетями**, оставив конечные точки PKI-протоколов доступными

### Эксплуатация и мониторинг
- **Обзор** -- четыре главных показателя, шаги первоначальной настройки и девять независимых карточек (очередь работ с действиями продления, повтора и публикации, состояние автоматизации, выпуск по источникам, горизонт истечения, соответствие, охват отзывом, иерархия, последние операции, ЦС и HSM), которые можно показывать, скрывать и переупорядочивать с пресетами раскладки, сохраняемыми для каждого пользователя, и которые сами обновляются при изменении данных
- **Отчёты** -- PDF-отчёты по расписанию, краткие сводки для руководства, отозванные сертификаты, пользовательские шаблоны
- **Инструменты для сертификатов** -- проверка SSL, декодер CSR/сертификатов, сопоставление ключей, конвертер форматов
- **E-mail-уведомления** -- SMTP со STARTTLS или неявным TLS (порт 465), **OAuth2 (XOAUTH2)** для Gmail, Outlook.com и Microsoft 365, настраиваемые HTML/текстовые шаблоны, оповещения об истечении сертификатов с несколькими порогами в днях (одно письмо на порог и период действия, по схеме 30/14/7/1), с возможностью исключить сертификаты, которые ACME-клиенты продлевают сами
- **Хуки развёртывания** -- отправка выпущенных и продлённых сертификатов, а также заново созданных CRL (DER или пакет PEM с CRL родителей) на удалённые хосты по SSH/SFTP, с путями назначения и необязательной командой перезагрузки для каждой привязки: аутентификация по ключу (созданный ed25519 или импортированный ключ, шифруется при хранении), закрепление ключа хоста при первом подключении, пути назначения для каждой привязки (сертификат / ключ / полная цепочка, цепочка без самоподписанного корня, если привязка его не требует, запись атомарная), надёжная очередь доставки с повторами и историей по каждой доставке, **пресет для того же хоста** для сервисов рядом с UCM и **цели HTTP API**, отправляющие сертификат на межсетевой экран, балансировщик или облачный API одним запросом из шаблона тела (URL, метод, зашифрованные заголовки, переменные вида `{{cert_pem|json}}`, закрытый ключ только при явном согласии и по проверенному HTTPS)
- **Резервное копирование и восстановление** -- ручные и плановые зашифрованные резервные копии с политиками хранения и необязательным потолком занимаемого сохранёнными архивами места; архивы представляют собой потоки независимо аутентифицируемых фрагментов, поэтому создание архива и его проверка перед восстановлением не держат его целиком в памяти; архивы содержат клиентские заказы ACME и ожидающие запросы, восстанавливаются в режиме слияния или замены, сопоставляют строки по имени между установками и повторно применяют миграции-исправления
- **Пакет диагностических журналов** -- загрузка в один клик (Settings → About → Diagnostic) журналов приложения, журнала ошибок, журнала systemd и диагностики системы без секретов в виде ZIP с замаскированными конфиденциальными токенами
- **Просмотр системных журналов** -- просмотр журналов приложения, доступа, ошибок и systemd из интерфейса с фильтрацией по уровню, периоду и тексту, секреты скрыты
- **Метрики Prometheus** -- включаемая по желанию конечная точка `/metrics` с доступом по bearer-токену, отдающая счётчики сертификатов, ЦС, планировщика, вебхуков и ACME
- **Планировщик** -- административный вид фоновых задач (проверки истечения, обновление CRL, доставка вебхуков, резервные копии, автопродление) со статусом и немедленным запуском, работает в отдельном процессе под gunicorn
- **HTTPS для самого UCM** -- применение любого выпущенного сертификата к веб-интерфейсу; привязка автоматически следует за продлениями (файлы создаются заново, служба перезапускается)
- **Безопасные сетевые настройки по умолчанию** -- прослушивание dual-stack (`HOST=::` обслуживает IPv6 и IPv4 на одном сокете) и защита административного Base URL (проверка доступности перед применением, каноническое перенаправление отключается, когда хост перестаёт разрешаться, переключатель аварийного восстановления `UCM_DISABLE_CANONICAL_REDIRECT=1`)
- **Обновление ПО** -- встроенная проверка обновлений с установкой в один клик, ежедневная проверка по расписанию в стабильном канале или канале релиз-кандидатов и необязательная автоматическая установка (DEB/RPM) с обязательной проверкой SHA256 и достоверными событиями результата (установлено только после проверки версии после установки), а также необязательное разовое окно с заметками о выпуске для каждого пользователя после обновления
- **Глобальный поиск** -- поиск по всем ресурсам и палитра команд (Ctrl+K)

### Платформа
- **Темы** -- Atelier и Aurore, каждая тёмная или светлая либо по настройке системы; **настройки пользователя хранятся на сервере** (язык, тема, режим)
- **i18n** -- 10 языков (EN, FR, DE, ES, IT, PT, UK, RU, ZH, JA)
- **Сохранение состояния интерфейса** -- выбранные фильтры сохраняются между перезагрузками на основных страницах-списках (сертификаты, ЦС, шаблоны, политики, журналы аудита, хранилище доверия, пользователи, SSH)
- **База данных** -- SQLite (по умолчанию) или **нативный бэкенд PostgreSQL** с интерфейсом двусторонней миграции
- **Адаптивный интерфейс** -- React 18 + Radix UI, удобен на мобильных устройствах
- **Реальное время** -- живые обновления по WebSocket: изменение, сделанное другим оператором, обновляет показывающие его списки, а переподключение после сбоя перезагружает их, не оставляя на экране устаревших строк
- **Мультиплатформенность** -- Docker, Debian/Ubuntu (.deb), RHEL/Rocky/Fedora (.rpm); пакеты устанавливают ротацию журналов доступа и ошибок
- **Готовность к обратному прокси** -- публичные порты не зависят от портов прослушивания (явный `:80` или `:443` в базовых URL сообщается как введён), доверенные прокси по IP или сети CIDR и значения `proxy.*` Helm-чарта для Ingress перед UCM

## Быстрый старт

### Docker

```bash
docker run -d --restart=unless-stopped \
  --name ucm \
  -p 8443:8443 \
  -p 8080:8080 \
  -v ucm-data:/opt/ucm/data \
  -v ucm-config:/etc/ucm \
  neyslim/ultimate-ca-manager:latest
```

Образ также доступен в GitHub Container Registry: `ghcr.io/neyslim/ultimate-ca-manager`. Вариант FIPS помечен тегом `<version>-fips` (запускайте его с `UCM_FIPS=1`).

### Debian/Ubuntu

Скачайте пакет `.deb` из [последнего выпуска](https://github.com/NeySlim/ultimate-ca-manager/releases/latest):

```bash
sudo dpkg -i ucm_<version>_all.deb
sudo systemctl enable --now ucm
```

### RHEL/Rocky/Fedora

Скачайте пакет `.rpm` из [последнего выпуска](https://github.com/NeySlim/ultimate-ca-manager/releases/latest): `ucm-VERSION-1.fc43.noarch.rpm` для Fedora, `ucm-el9-VERSION-1.el9.noarch.rpm` для RHEL, Rocky Linux и AlmaLinux 9, `ucm-el10-VERSION-1.el10.noarch.rpm` для тех же дистрибутивов версии 10.

```bash
sudo dnf install ./ucm-VERSION-1.fc43.noarch.rpm
sudo systemctl enable --now ucm
```

**Доступ:** `https://localhost:8443` или `https://your-server-fqdn:8443`
**Первый вход:** `admin` с паролем, сгенерированным при первом запуске: `sudo cat /opt/ucm/data/initial-admin-password` (Docker: `docker exec <container> cat /opt/ucm/data/initial-admin-password`). Его необходимо сменить при первом входе. О том, как задать свой пароль, см. [First access](docs/installation/README.md#first-access).

Все способы установки, включая Docker Compose и установку из исходного кода, описаны в [руководстве по установке](docs/installation/README.md).
